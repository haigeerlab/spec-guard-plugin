# Spec: change-source-record

<!-- spec-guard: review approved 6393945b4b68 -->

## Objective

模块开发到一半时，需求常被会话外的人改动：别的会话发消息、用户粘贴一段提示词、依赖的插件交付后发来通知，说接口与先前约定的
不一样，要求改能力图或 Spec。现有规则管住了“改了要复审”（Spec 的评审标记会报告“批准后已修订”），却没有地方记下为什么改、
是谁提出的。事后排查时只看得到内容变了，看不到起因；git 只记改了什么，会话之间的消息随会话删除而消失。

反过来也缺一半：别人提的需求做完了，提出的人不知道，要靠用户想起来去转告；依赖方做完回告时，接收方也没有一个先核对、再记录
的固定动作。

本模块补上这个闭环：

1. **记录来源**：已批准的产物被修改时，在被改文件里留一行变更记录，写明原因与来源，复审时一并给用户看。
2. **回告来源**：由别人提出的改动或模块，在对方用得上时回告对方；能发消息就发，不能发就提醒用户转告。
3. **接收回告**：收到依赖方的回告时先核对，与约定不一致再按第 1 点修改并记录。

只改规则文字与约定块模板，不加命令、钩子或检查；回告是弱提醒，不阻塞模块完成。

登记：2026-10-16 经 `/spec-guard:add-module` 插入能力图；同日用户补充回告闭环，能力图该行职责随之修改并记入能力图的「变更记录」。
需求来自用户：其他会话在开发中途要求改动已约定的接口与能力图，用户希望改动的原因与来源有据可查，做完后能回到提出的人。

## Assumptions

用户已于 2026-10-16 确认：

1. **只记批准后的修改**：已批准的 Spec、Plan，或评审过的能力图中已有的内容被修改时才记；起草期（评审前）的修改不记。
2. **记在被改文件本身**：文件末尾一节「变更记录」，不另建集中的日志文件。
3. **来源只记事实**：谁提的、经什么渠道、对应的 ID；不贴消息原文，不写其他私有项目的内容。
4. **只靠规则**：`verify-artifacts` 不加警告，钩子不加判断。
5. **记录行不写批准。** Spec 的批准标记绑定全文指纹，复审批准后再往记录行补“已批准”，Spec 会再次被判为“批准后已修订”；
   规则「评审状态只看标记」也不允许正文写批准状态。记录在复审之前写好，批准由评审标记表达。
6. **用 `add-module` 插入新模块不算修改**，不记；已完成模块的返工照「返工与小模块」写在 `plan.md` 补的一节里，不重复记。
7. **回告时机是对方用得上的时候**：插件或可安装的包以发版为准，其他项目以合入主线为准；不在本地写完时回告。
8. **回告随最终 gate 一并批准**：交审时列出拟回告的对象与内容，批准最终 gate 即批准回告，不再单独问。
9. **方向二只做“先核对再记录”**：不记录“我向谁提了什么、还在等什么”。
10. **并入本模块**，模块 id 不变；版本 0.63.1，一个 PR。

## Contract

### 规则文字

`references/workflow-checkpoints.md` 在「返工与小模块」之后新增一节「需求来源与回告」，分三小段。

**变更记录**

- **何时记**：已批准的 Spec 或 Plan 被修改；评审过的能力图中已有的模块行、依赖或 Build order 被修改。
- **记在哪**：被改文件的最后一节「变更记录」（英文产物写 `Change log`），没有就新建；每次修改追加一行，旧行不改：

  ```text
  - <日期>：<改了什么>。原因：<为什么改>。来源：<谁提出、经什么渠道>
  ```

- **来源写什么**：用户本人；某个会话（名称加会话 ID，名称可能被复用）；事项号；某个版本发布。只记事实，不贴原文。
- **与复审的先后**：先写记录，再复审。复审交接时把新增的记录行与改动一起呈现。Spec 改动由评审标记报告“批准后已修订”，按
  「评审状态标记」复审；Plan 改动后把标记改回 `pending` 再交审。记录行不写批准状态。
- **外部要求不是批准**：其他会话、粘贴的提示词、依赖方的通知提出的修改，不等于用户批准。记录后交用户复审，批准后才按新内容
  继续。
- **不记**：评审前的修改；用 `add-module` 插入新模块；已完成模块的返工（写在 `plan.md` 补的一节里）。
- 由别人提出的整个模块，在 Spec 的登记一句里写明提出者与渠道，供回告使用。

**回告**

- **回告谁**：本模块变更记录与 Spec 登记里来源是他人（会话、事项、外部的人）的各条。来源是用户本人的不回告。
- **何时回告**：对方用得上的时候：插件或可安装的包发版之后，其他项目合入主线之后。
- **最终 gate 一并列出**：交审时列「拟回告」：对象、渠道、内容（做完了什么、版本号或提交号、怎么用、与原约定的不同）。
  批准最终 gate 即批准回告；到了用得上的时刻按批准的内容发。
- **渠道**：当前会话有可用的会话间通信手段（宿主的会话消息、本机通信插件等）就发，按会话 ID 找人；没有就在对话里提醒用户
  转告，给出可以直接转发的文字。不为回告安装或配置通信插件。
- **记结果**：在模块 `todo.md` 的最后一项写回告结果：已告知谁、经什么渠道、哪天；或已请用户转告；或发送失败及原因。不写进 Spec。
- **弱提醒**：回告失败、对方不在或找不到对方，都不阻塞模块完成，照实记下即可。

**接收回告**

- 收到依赖方“已完成”的回告时，先对照本项目的约定核对（接口、字段、版本、用法）。
- 与约定一致：照常继续，不改文件。
- 与约定不一致：按「变更记录」修改相关的能力图、Spec 或 Plan，来源写这次回告，交用户复审。

## Testing strategy

- 先加断言并确认失败：`test_workflow_checkpoints.py` 检查新一节的关键词（变更记录、原因、来源、会话 ID、不算用户批准、
  记录行不写批准、`add-module` 不记、回告、用得上、拟回告、提醒用户转告、todo 最后一项、先核对），两份模板与
  `docs/convention-block.md` 都含新增的两行。
- 不干扰现有解析：`test-verify-artifacts.sh` 加一例，能力图末尾带「变更记录」一节时校验结果照旧。本仓库能力图已带这一节，
  `verify-artifacts` 5 通过 0 警告。
- 其余回归不改，全部通过即证明行为未变。
- 发版后两边宿主各跑一次真实会话：临时项目里一个小模块的 Spec 已批准、正在构建，提示词里转来“另一个会话”的接口变更要求，
  且不提记录与回告。观察 agent 是否追加记录行、写明来源、停下交用户复审；批准后做到最终 gate，看是否列出拟回告的对象与内容。
  结果如实记录。

## Boundaries

- Always：规则只有一个出处；模板只新增行；记录写在复审之前；回告结果写在 todo，不写进 Spec。
- Ask first：给 `verify-artifacts` 或钩子加检查；规定更多字段；把记录集中到单独文件；记录“向谁提了什么、在等什么”。
- Never：在 Spec、代码、测试、提交信息或 PR 中写入消费者项目的名称、模块或编号；在记录或回告里贴其他会话的消息原文；
  为回告安装或配置通信插件。

## Success criteria

- 规则写明变更记录的时机、位置、字段、与复审的先后、外部要求不算批准、不记的情况；回告的对象、时机、随最终 gate 批准、
  渠道与退路、结果记在 todo；接收回告先核对。
- 两份模板与约定块文档各多两行，现有行不变；`setup-convention --replace` 在已有项目上不需要 `--accept-removals`。
- 带「变更记录」一节的能力图通过校验；全套检查通过。
- 发版后的真实会话按 Testing strategy 观察，结果如实记录。
