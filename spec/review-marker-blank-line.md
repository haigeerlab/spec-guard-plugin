# Spec: review-marker-blank-line

<!-- spec-guard: review approved 78d8362f6576 -->

## Objective

使用者项目的前端用 `oxfmt --check` 做提交前检查（lint-staged 配置是 `'*': 'oxfmt --check'`）。协调会话用 review-mark 写完标记再提交时，
提交被钩子拒绝：样本 Spec 的第 1 行是标记，第 2 行紧接着是标题。

`hooks/review_mark.py` 自己插入标记时带空行：首行是标题，就写成「标题、空行、标记」；首行不是标题，就写成「标记、空行、正文」。出问题的是
**原地替换**：文件里已经有标记时（例如起草时 agent 把 `pending` 手写在第 1 行、紧贴标题），它只换掉那一行、不动位置，所以贴着的行原样留下。

2026-10-18 用前端的 `oxfmt` 只读检查了五种写法（标记内容相同）：

| 写法 | 结果 |
|---|---|
| 文件第 1 行是标记，紧接标题 | 不合格 |
| 文件第 1 行是标记，空一行再标题 | 合格 |
| 标题紧接标记，标记后空一行 | 不合格 |
| 标题、空行、标记，标记后紧接正文 | 不合格 |
| 标题、空行、标记、空行、正文 | 合格 |

也就是说，标记前后都要有空行，只有在文件开头时前面不用。本模块让 review-mark 每次写标记时都保证这一点。

## Assumptions

用户已于 2026-10-18 确认按「各一个模块、合发一个补丁版本」做；下面几条是本 Spec 的设计取舍，随本 Spec 一并审：

1. **只在 review-mark 写标记时整理空行。** 已批准、之后不再写标记的文件不动：补空行会改变指纹，只为格式让已批准的 Spec 变成「批准后已修订」，
   代价大于收益。
2. **前后各保证一个空行。** 标记前一行不是空行（且标记不在文件开头）就补一个；标记后一行不是空行（且不在文件末尾）就补一个；已有空行不重复加，
   多余的空行不删。三种情况都适用：原地替换、在标题后插入、在文件开头插入。
3. **补在算指纹之前。** approve 时指纹按写好 pending 之后的文本计算（`review_mark.py` 现有做法），空行在这一步就已经补上，所以写进去的指纹与
   文件内容一致；预览的差异里能看到补的空行。
4. **读取不改。** 读取标记本来就不看位置，有没有空行都认，不需要改。
5. **不检查其他格式。** 只管标记行两侧的空行，不引入任何格式化工具，不改文件其他部分。

## Contract

`hooks/review_mark.py` 的 `_with_marker(text, marker)`：

- 找到已有标记（原地替换）：替换那一行后，保证这一行前后都是空行（文件开头和末尾除外）。
- 没有标记、首行是标题：结果是「标题、空行、标记、空行、其余正文」；其余正文本来就以空行开头时，不再多加。
- 没有标记、首行不是标题：结果是「标记、空行、正文」（现有行为）。
- 换行符照现有做法：`review_mark.py` 按通用换行读入、以 `\n` 写回，`\r\n` 文件写回后是 `\n`；补的空行同样是 `\n`。本模块不改读写方式。
- `_marked` 与 approve 时的指纹计算方式不变，仍然基于整理过空行的文本。

预览照旧给出完整差异，补的空行会出现在差异里。其他命令、钩子、`verify-artifacts`、阶段判定不变。

## Testing strategy

- 先写断言并确认变红（`test_review_marker.py`）：
  - 上表五种写法的 pending 和 approved 各写一次，结果都是「标记前后都有空行（文件开头除外）」；原本已经合格的写法不多加空行。
  - `\r\n` 文件写回后是 `\n`，标记两侧的空行齐全（与现有读写方式一致）。
  - approve 后，文件里的指纹等于按最终文件重新计算的指纹，阶段判定为已批准，不是「批准后已修订」。
  - 标记在文件末尾、后面没有内容时，不在后面补空行。
- 其余回归不改，全部通过即说明行为没有别的变化。
- 用前端的 `oxfmt --check` 只读复查 review-mark 写出的五种样本，记录退出码。

## Boundaries

- Always：只在写标记时整理标记行两侧；先整理、再算指纹；预览里看得到改动。
- Ask first：批量整理已批准文件的空行；引入格式化工具或检查；改读取标记的规则。
- Never：只为格式改动已批准文件、导致它变成「批准后已修订」；在仓库文件、提交信息或 PR 中写入其他私有项目的名称、模块或编号。

## Success criteria

- review-mark 写出的标记，前后都有空行（文件开头除外），五种样本过 `oxfmt --check`。
- approve 写入的指纹与最终文件一致；已有空行不重复添加。
- 全套检查通过；修复发版后把版本号告诉报告方（事项 75SV50T）。
