# Spec: tables-at-acceptance

<!-- spec-guard: review approved 9da7dce5e893 -->

## Objective

最终验收的改动文件清单写成表格时最清楚；但规则只要求「分新增、修改、删除并带行数」，用不用表格全看 agent。文档改动混在
文件清单里也看不出来：一次验收里改了两份文档，用户从清单里看不到。文档是留给其他开发者的技术沉淀、架构与使用说明，和代码
分开看更清楚。提交清单与新增依赖挤成一行时同样看不清。

本模块把「最终验收列出实际改动的文件」一条的呈现方式定下来：有内容的项用表格，没有内容的写一行「无」；写给人读的文档单独
一张表放在最前。

登记：2026-10-19 经 `module-insert.py` 插入能力图。用户在本会话看过 commits-at-acceptance 的验收截图后提出，经两轮效果示例
确认呈现方式。

## Assumptions

用户已于 2026-10-19 确认（以对话里的完整效果示例为准）：

1. **有内容就用表格，没有就写一行「无」。** 适用于改动文件、新增依赖、本模块的提交。
2. **文档单独一张表放在最前。** 写给人读的文档：如 README、文档目录、CHANGELOG、文档基线里登记的文档；按用途判断，不按扩展名
   （规则文件、模板即使是 `.md` 也算其他改动）。spec、plan、todo 不单独成组，放进其他改动。
3. **改动文件的表列**：状态、文件、行数。文件多时仍按目录归并，一行写目录与文件数。
4. **新增依赖的表列**：包、版本、运行时或开发、为什么加；锁文件不列表，只写有没有改动和行数；工作区自己的包照旧不算。
5. **提交的表列**：提交号、做了什么、对应任务；多时按任务归并；待提交一行放最后。
6. **不做**（自查认定过度）：规格文件单独成组；超出影响面、范围内增补、Spec 修订三项一律写「无」；「文档建议」改名。
   小标题与其他各节的写法不规定。
7. **不改版本号、不发版**；CHANGELOG 并入顶部「[未发布]」段，和 commits-at-acceptance 一起排到下一版。

## Contract

`references/workflow-checkpoints.md`「Plan 检查点分级」一节，「最终验收列出实际改动的文件」一条改为：

> **最终验收列出实际改动的文件。** 模块 Plan 的最后一个 `gate` 检查点，除开头的五件事外，还要在对话里列出本模块相对
> 开始前实际改动的文件：用表格（状态、文件、行数），分新增、修改、删除并带行数，取自版本库的差异统计，不凭记忆；写给人读的
> 文档（如 README、文档目录、CHANGELOG、文档基线里登记的文档，按用途判断、不按扩展名）单独一张表放在最前，没有就写
> “文档改动：无”；文件多时按目录归并（一行写目录与文件数）、只展开关键文件；单独标出超出 Plan 预计影响面的文件并说明原因，
> 没有就写“无”。（项目没有按任务提交、不在版本库、并行边界几句不变。）
> 再列本模块新增的直接依赖（取自依赖清单的差异，不凭记忆；不含工作区自己的包，即 `workspace:` 引用或本仓库内的包）：有就用
> 表格（包、版本、运行时或开发、为什么加），锁文件只写有没有改动和行数；都没有写“新增依赖、锁文件改动：无”。这里是用户看
> 新增包的地方。
> 再列出本模块的提交：取自版本库的提交记录，不凭记忆，用表格写提交号和一句话（做了什么）及对应任务，多时按任务归并；最终验收
> 批准后才做的那次提交（勾选与状态记录）写作待提交，放在最后一行。随后推送或开 PR 时，推上去的提交和这份清单不一致的，单独列出差异。

两份 `templates/*-block-local.md` 与 `docs/convention-block.md` 的摘要行改为：

> 模块最终验收时在对话里用表格列出实际改动的文件（新增、修改、删除与行数，取自版本库；写给人读的文档单独一张表放在最前）、
> 本模块的提交（提交号＋一句话）及新增依赖与锁文件改动（不含工作区自己的包；锁文件只写有没有改动），没有内容的写“无”，
> 推送或开 PR 时与这份提交清单不一致的单独列出；任务做完的结果带文件数与提交号；

`CHANGELOG.md`「[未发布]」段加一条。阶段判定、阶段提示、`verify-artifacts`、命令行为与版本号都不变。

## Commands

```text
python3 -B plugins/spec-guard/hooks/test_workflow_checkpoints.py
/bin/bash scripts/verify-and-commit.sh -- -m "<信息>"
```

## Testing strategy

- 先加断言并确认失败：`test_workflow_checkpoints.py` 最终验收用例补关键词（用表格、单独一张表放在最前、按用途判断、
  文档改动：无、一行写目录与文件数、为什么加、对应任务）；模板与 `docs/convention-block.md` 补「用表格列出」「单独一张表放在最前」。
- 已有断言（新增、修改、删除，差异统计，新增的直接依赖，工作区自己的包，提交号和一句话等）保持通过。
- 发版后两边宿主各跑一次真实会话，看最终验收是否按表格呈现、文档单列在前。

## Boundaries

- Always：规则只有一个出处；摘要行只指向它。
- Ask first：为它加检查或钩子；规定小标题或其他各节的格式。
- Never：在 Spec、代码、测试、提交信息或 PR 中写入消费者项目的名称、模块或编号；本模块里改版本号。

## Success criteria

- 规则写明三类表格、文档单列在前、没有内容写「无」、按目录归并与锁文件一行。
- 两份模板与 `docs/convention-block.md` 的摘要行同步。
- 全套检查通过，版本号不变。
