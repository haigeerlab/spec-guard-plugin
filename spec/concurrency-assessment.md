# Spec: concurrency-assessment

<!-- spec-guard: review approved 4dc735765530 -->

## Objective

并行开发值不值得做，取决于能力图拆得怎么样：有没有几个模块能同时开工、会不会都去改同一批文件。这些在拆模块的时候最容易看清，
开工以后再调整就要动已经写好的 Spec。本模块在**能力图评审**这个停点（和文档建议同一停点）加一段并行评估：开关
`moduleConcurrency` 为 `on` 时，agent 在交审正文里给出评估结论，形式是「Build order 里哪些模块可以写成逗号组、哪些模块值得往前挪」。

本模块只改共享检查点规则的文字和对应回归，不改任何代码、不改阶段提示。开关为 `off` 或未设置时，这一节对 agent 不生效，
插件的所有输出与上一版逐字相同。

登记：2026-10-18 经 `/spec-guard:add-module` 插入能力图（同批 7 个模块）。来源：用户本人，经多模块并行需求讨论（2026-10-17～18），
需求记录第 5 节 A1、A2。

## Assumptions

1. **只在两个时机评估。** 一是能力图评审（写完或大改能力图、交用户确认模块拆分时）；二是中途接手的项目、用户明确要求评估时。
   用 `add-module` 插入单个模块不算能力图评审，不评估；阶段提示也不每轮提醒（需求记录 A1）。
2. **怎么知道开关开着。** 上一个模块定了开关不注入阶段提示，所以规则写明：到了能力图评审停点，先用 `/spec-guard:config`
   （Codex：`spec-guard-ops` 的 config）查看 `moduleConcurrency`，不是 `on` 就跳过这一节，交审内容和以前一样。
3. **两条硬门槛，任一不满足就写「不建议并行」并说明缺什么：**
   - 至少有一波能同时开工 2 个及以上模块：这些模块之间没有依赖，或依赖的模块已经完成，或接口已经在提供方 Spec 里定好；
   - 有干净的集成基线：集成用的本地分支没有未提交改动，项目 Spec 的 Commands 一节里的完整检查能在本地跑通。
     没跑就写「未核实」，不当成满足。
4. **三项参考，不卡结论，只影响建议：** 文件分区（各模块是否改不同目录）、共享接口（有没有多个模块要用、但还没定的接口）、
   热点文件（锁文件、根配置、迁移、测试资源这类人人都要改的文件）。
5. **结论的写法：**
   - 给出建议的 Build order 改法：哪几个模块写成逗号组、哪些模块往前挪、为什么；
   - 关键路径（最长的依赖链）和每个模块挡住的下游模块数**只在这里算**，不进 `/map`，也不写进能力图；
   - 按能否独立开发给出拆分建议：同时进行的模块不改同一批文件，依赖要么已合入、要么接口已定；能粗就粗，
     不为并行把模块拆碎（需求记录 A2）；
   - 只是建议。改 Build order 仍是改能力图，用户采纳后按现有规则修改并记变更记录。
6. **衔接任务和联调模块沿用现有规则。** 模块之间的衔接默认写成上一模块追加的任务或下一模块的第一个任务；只有牵涉多个并行模块、
   或要改不归任何模块的文件时，才建议单设联调模块。「公共预置」是普通模块，排在第一次有 ≥2 个模块同时开工之前。
7. **不写进约定块。** 约定块会被写进用户项目的 CLAUDE.md／AGENTS.md，加一行就会让 off 的项目也多一行文字。所以只改共享规则
   `references/workflow-checkpoints.md`：在「文档建议」一节的能力图评审一条后指向新的一节「并行评估（moduleConcurrency 为 on 时）」。
   约定块里本来就有「能力图评审……细则见共享检查点规则」这一句，agent 到这个停点时会读到。
8. **不写计算脚本。** 波次、关键路径都由 agent 按能力图的依赖列推算。样本项目只有十几个待做模块，手算可行；大项目算错的风险
   放进 Ask first，真需要时另开模块做只读计算。

## Contract

### `plugins/spec-guard/references/workflow-checkpoints.md`

- 「文档建议」一节的「能力图评审」一条末尾加一句：开关为 `on` 时，同一停点还要给出并行评估，见「并行评估」一节。
- 新增一节 `## 并行评估（moduleConcurrency 为 on 时）`，放在「文档建议」之后、「按需求批量前置审」之前。内容按上面假设 1～6 写，
  第一句写明：开关不是 `on` 时整节不适用。
- 新内容不出现 `parallel-`／`parallel_` 字样（`check-no-parallel-surface.py` 扫描整个插件目录）。

### 交审要点

「交审要让用户看到内容」一条列的是 Spec、Plan 的要点，能力图评审不在其中，不改。并行评估写在能力图评审的交审正文里，由新一节规定。

### 文档

CHANGELOG 未发布小节加一条「新增」；`docs/design.md` 讲到能力图评审停点的地方（如有）补一句。

## Commands

```bash
python3 -B plugins/spec-guard/hooks/test_workflow_checkpoints.py
python3 scripts/check-no-parallel-surface.py
/bin/bash scripts/validate.sh
```

## Testing strategy

- **`test_workflow_checkpoints.py` 先写失败的测试：**
  - 共享规则里有「并行评估」一节，节首写明开关不是 `on` 时不适用；
  - 这一节写到两条硬门槛、三项参考、逗号组与前移建议、关键路径只在这里算；
  - 「文档建议」一节的能力图评审一条指向它；
  - 约定块模板（`templates/*-block-*.md`）里**不出现** `moduleConcurrency`（证明 off 项目写入的约定块逐字不变）。
- **off 时逐字不变：** 本模块不改 hook 和模板，阶段提示与 verify-artifacts 的两套回归原样全绿即为证明；另外用 `git diff --stat`
  确认改动只落在共享规则、测试、CHANGELOG 和本模块的流程文件里。
- **改坏验证：** 删掉节首的「不是 on 时不适用」一句，确认对应断言变红；在约定块模板里加一个 `moduleConcurrency`，确认「模板里不出现」
  一例变红。两处都复原。
- **未验证：** 规则文字能不能让 agent 在真实的能力图评审里给出合格评估，单元测试证明不了，留给需求记录的第 7 关在样本项目上实测。

## Boundaries

- Always：开关不是 `on` 时这一节不生效；评估只出建议，改 Build order 仍要用户批准并记变更记录；没核实的门槛写「未核实」。
- Ask first：写一个只读脚本计算波次与关键路径；把评估结论写进 `/map` 或能力图文件；在阶段提示里提醒评估。
- Never：在约定块里加并行相关的行；因为评估结论自动改 Build order；为了并行把模块拆碎。

## Success criteria

1. 开关为 `on` 时，共享规则要求 agent 在能力图评审的交审正文里给出并行评估：两条硬门槛的结论、三项参考，以及 Build order 的逗号组
   与前移建议。
2. 开关为 `off` 或未设置时，插件的所有输出逐字不变，约定块模板不出现这个键。
3. 新增内容通过 `check-no-parallel-surface.py`。

## 文档建议

无。这一节本身就是给 agent 的规则；面向用户的说明等 `crew-interface` 统一写。
