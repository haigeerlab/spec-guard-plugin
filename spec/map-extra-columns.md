# Spec: map-extra-columns

<!-- spec-guard: review approved ef28f3c3898d -->

## 目标

两件来自使用方的小事，一起修（总账 S51、S68，2026-11-09 经 ecosystem-lead 追问）：

1. **能力图有额外列时 add-module 插不进去（S51）。** 能力图的严格解析允许模块表在 `Module id`、`Responsibility`、`Depends on`
   之后再加列（例如「本轮状态」），只要每行格数与表头一致。但 `module-insert.py:190` 生成新行时固定只写三格，插入后的能力图
   通不过严格校验，预览报「插入后的能力图未通过严格校验：模块表存在不完整的行」。2026-11-09 在 0.86.6 上复现。带额外列的项目
   因此完全用不了 `/spec-guard:add-module`（包括 `--proposal` 晋级，它走同一个 `preview`）。
2. **`/map` 的「可以开始」容易被读成「本轮要做」（S68）。** `ready`（🟢 可以开始）的判据只是依赖都已完成；一个使用方项目里 7 个
   不在当前阶段的模块也显示可以开始。spec-guard 没有「本轮」概念，排期由使用方决定；本模块只把这层意思写进说明。

给谁用：在能力图里加了自定义列的项目，以及读 `/map` 安排工作的人和 agent。

## 假设

用户已于 2026-11-09 确认（「按建议办」「说完了，开模块」，针对本会话的核对结论与需求总结）：

1. **补齐列数**：`module-insert.py` 生成新行时读模块表表头的实际列数；前三格照旧是 id、职责、依赖，第四格起留空（`|  |`）。
   不读、不推断额外列的内容。
2. **预览说明**：表头有额外列时，预览在「新行」之后多一行，写明哪些列留空，例如 ``额外列 `本轮状态` 留空，需要时自己填``。
   三列能力图不出这一行，新行、预览与写入结果与 0.86.6 逐字相同。
3. **校验不放宽**：严格解析、行摘要、Build order 校验都不改；额外列留空本来就合法。
4. **说明（S68）**：`commands/map.md` 讲状态的那段、`docs/commands.md` 的 map 条目、`docs/concepts.md` 术语表补一句：
   「可以开始」只表示依赖都已完成，不代表本轮要做，本轮做哪些由项目自己排（例如在能力图里加一列）。JSON 的 `ready` 与表格文字不改。
5. **不做**：不加「本轮」概念；不改 `activeModule` 相关行为（S70 交 module-crew）；不改 `interface.json`。
6. 发 0.86.7；发版后回告 ecosystem-lead（回复 #19453）；仓库里不出现消费项目的名字、模块或编号。

## 边界

- Always：先红后绿；只补空格与一行说明，校验与已有行不动。
- Ask first：给额外列填默认值；读额外列内容参与判定；加「本轮」概念；改 `ready` 的判据或文字；改 `interface.json`。
- Never：在 Spec、代码、测试、提交信息或 PR 中写入消费项目的名称、模块或编号。
