# Spec: review-card-sections

<!-- spec-guard: review approved 79cac249b485 -->

## Objective

一个真实的项目接入决策收件箱后，用户会在两个地方看到同一次交审：模块会话的对话正文，以及决策收件箱的卡片。两处小项的
名称、顺序不一样，同一件事要换个地方重新找；问用户怎么答复时，推荐答复有时写成行内代码、有时不写，用户手抄会带进多余的
标点。决策收件箱一方已经把每类审批的固定小项和复制块规则定成模板，session-protocol 契约正在把每类的「类型」取值写进
【等待用户】。

本模块让 spec-guard 共享检查点规则里，自己产生的交审和请示与这份模板对齐：

1. **小项统一，内容不删**：五类审批（能力图审阅、Spec、Plan、中途 gate、最终验收）在对话正文里按模板的小项名称和顺序给出；
   模块会话里每一项照旧写全（验收标准逐条列 AC，最终验收的文件、依赖与提交照旧用表格）。精简成十几行卡片的是决策收件箱，
   spec-guard 不照搬。
2. **怎么批准**：推荐答复放进一个独立的可复制代码块；不需要用户回答的内容不用代码块；每个选项写清选了之后会怎样。
3. **稳定接口**：`interface.json` 只增一节，写出 spec-guard 产生的第 1～6 类（能力图审阅、Spec、Plan、中途 gate、最终验收、
   卡住时选做法）的名称、小项，以及各自对应契约【等待用户】「类型」的哪个取值，供 module-crew 与决策收件箱对齐。

登记：2026-10-19 经 `module-insert.py` 插入能力图，用户在本会话批准插入。需求来自决策收件箱一方的需求文档（SG-1～SG-3），
处理口径由用户在 spec-guard 插件负责人会话里定：SG-1 小项统一、内容不删；SG-2 照做；SG-3 只写第 1～6 类。

## Assumptions

1. **小项名称与顺序以模板为准，契约定稿后对齐（待对齐）。** 模板第四节与契约 v2.3 草案的小项名一致；契约尚未定稿，
   定稿时名称有改动，在本模块内改到一致后再交最终验收。
2. **现有要求并进对应小项，一条不丢：**
   - Spec：「范围内与范围外」→「做／不做」；开关 on 时的并行边界也写在「做／不做」；「关键决策与取舍」→「要你确认的假设」
     （agent 已经替用户选了的，就是要用户确认的前提）；「未决问题」与 Spec 交审的文档建议 →「附带的小决定」（每个写清选项）；
   - Plan：「每个任务与它的验证方式」→「分几步」；「影响面」→「会改哪些文件」；「检查点及其类型」→「中途会停下来问你的地方」，
     列出 `gate` 并写明是否含推送与开 PR，没有中途 gate 写「无，做完直接交最终验收」；
   - 能力图审阅：「文档建议」与并行评估各有落点（文档建议单列一项，并行评估写进「先后顺序」）；
   - 中途 gate 与最终验收：开头「五件事」落在小项里，五件事那一节本身不改；最终验收的文件表、依赖表、提交表、超出影响面与
     超出并行边界，全部写在「改了哪些文件」一项；Spec 修订差异写在「Spec 中途改过吗」一项。
   - 「写明这次批准授权什么」→ 小项之后独立一行「批了会怎样：」。
3. **「注意」「批了会怎样」是小项之后的独立行，不算小项**（契约负责人要求，已答应）。「注意」写遗留建议、没验证到的、偏离计划的
   地方，没有写「无」；五类审批都写。「推荐理由」跟在推荐答复前。
4. **combined 节奏**：Spec 五项再接 Plan 四项，一次交审；对应契约类型「Spec 与 Plan」。
5. **卡住时选做法**（「同一模块、同一目标第二次过不去」那条）：写「出了什么事」，再列各个做法与代价，给推荐。它不是审批，但要回复，
   也适用复制块规则。
6. **复制块只装推荐答复**：内容是最短的可接受说法（例如 `批准`；有附带的小决定时合成一行，例如 `批准；D1 A`），用不带 shell
   语言标签的代码块，不用行内代码。同一次交审只给一个复制块。交审消息里不需要用户回答的内容（文件原文、日志、命令输出、示例、
   Spec 改动差异）不用代码块：差异写成改前改后对照或引用块。要用户发出去的斜杠命令照旧用代码块（「按需求批量前置审」那条不变）。
7. **接口按契约代码列出，只增不改**：`interface.json` 新增顶层 `reviewKinds`，键是契约代码，接口版本 1.4 → 1.5。第 7 类「去会话操作」
   与 module-crew 的「接口提案」不归 spec-guard，不写。契约草案的代码（待对齐）：

   | 类别 | 契约取值 | 契约代码 |
   |---|---|---|
   | 能力图审阅 | 能力图审阅 | `capability-map` |
   | Spec 交审 | Spec | `spec` |
   | Plan 交审 | Plan | `plan` |
   | Spec 与 Plan（combined） | Spec 与 Plan | `spec-plan` |
   | 中途 gate | 中途检查点 | `checkpoint` |
   | 最终验收 | 最终验收 | `final` |
   | 卡住时选做法 | 卡住选做法 | `stuck` |

8. **约定块模板不改。** 两份模板与 `docs/convention-block.md` 那一行「交审 Spec 或 Plan 时在对话里呈现内容要点…」仍然成立；
   改它会让既有项目升级时 `--replace` 多一次删除确认。细则只写在共享检查点规则，三处镜像（`commands/review-mark.md`、
   `skills/spec-guard-ops/SKILL.md`、`docs/commands.md`）同步。
9. **不改钩子判定，不改版本号，不发版**；CHANGELOG 写进「[未发布]」段，和 #384、#385 一起排到下一版。

## Contract

`references/workflow-checkpoints.md`「批准标记」一节：

**「交审要让用户看到内容」改为按类别列小项**（名称与顺序如下；每项内容按现有要求写全）：

| 类别 | 小项（按顺序） |
|---|---|
| 能力图审阅 | 拆成哪些模块（新插入的标「新」）、先后顺序（开关 on 时含并行评估）、文档建议（README 一定表态，没有写「无」） |
| Spec | 目标、做／不做、要你确认的假设、验收标准（按 AC1、AC2… 逐条全列）、附带的小决定（未决问题与文档建议，没有就不写） |
| Plan | 分几步（每个任务与它的验证方式）、会改哪些文件（影响面，有没有新增依赖、碰不碰公共文件）、风险、中途会停下来问你的地方 |
| 中途 gate | 做到哪了（完成了哪几步、测试结果）、为什么停在这、接下来要做的那一步 |
| 最终验收 | 做了什么、验收结果（按 AC 逐条给证据，完整检查结果）、改了哪些文件（「最终验收列出实际改动的文件」那几张表）、Spec 中途改过吗 |

小项之后两行：「注意：」与「批了会怎样：」。combined 节奏 Spec 五项接 Plan 四项。短文件可以贴全文、只给链接不算交审、写在
确认框之前、用户没看到内容时的批准不记为 `approved`，这几句不变。

**「交审时说明怎么批准」改为：**

> 呈现内容之后列出选项，每个选项写清选了之后会怎样：会发生什么、能不能撤回、哪些事还要另外问用户（例如批准 Spec 后写 Plan
> 还会再问；批准最终验收后合并撤不回，推送仍要另外同意；退回时写明怎么回意见）。再写「推荐理由」，最后把推荐答复放进一个
> 独立的可复制代码块（不带 shell 语言标签，不用行内代码），内容是最短的可接受说法，附带的小决定合成一行。只有要用户回答时才
> 出代码块；不需要回答的内容不用代码块。“继续”不会被记为批准。这些都不能替代内容；不要等用户说了“继续”再解释。

「同一模块、同一目标第二次过不去」一条补一句：交用户决定时写「出了什么事」，各做法写清代价，给推荐，复制块规则同上。

`interface.json`：`interface` 改为 `"1.5"`，新增顶层：

```json

  "appearsWhen": "always (interface 1.5); the kinds of user decision spec-guard's shared checkpoint rules produce, add-only",

  "kinds": {

    "spec": {"label": "Spec", "sections": ["目标", "做／不做", "要你确认的假设", "验收标准", "附带的小决定"]},
```

每类的 `sections` 与共享检查点规则里的小项名一致（逐个能在规则文件里找到），`commonLines` 三项都在规则里。

## Testing strategy

- 先加断言并确认失败：`test_workflow_checkpoints.py` 为五类审批各加一例，断言小项按顺序出现（取位置比较先后）；断言
  「注意：」「批了会怎样：」、combined 合写、卡住时「出了什么事」；「交审时说明怎么批准」断言可复制代码块、不用行内代码、
  不需要回答的不用代码块、能不能撤回、还要不要另外问、“继续”不会被记为批准。
- 已有断言（范围内与范围外、关键决策与取舍、未决问题、验证方式、检查点及其类型、影响面、只给链接不算交审、最终验收的表格等）
  不改、保持通过：它们就是「内容不删」的回归。
- `test-checkers.sh` 加反例：`reviewKinds` 少一类、多一类、某类小项名在规则里找不到，各自报错；正例放行。
- 变异核对：在草稿副本上删掉某类的一个小项名、或把复制块改回行内代码，确认对应断言变红。

## Boundaries

- Always：小项细则只写在共享检查点规则一处，三处镜像只摘要并指向它；接口只增不改。
- Ask first：契约定稿的写法和本 Spec 不一致、需要改范围时；改约定块模板；给交审格式加钩子或检查。
- Never：在仓库文件、提交信息或 PR 中写入私有项目名或其模块、事项编号；本模块里改插件版本号；写第 7 类「去会话操作」或
  「接口提案」；删减模块会话里任何一项的现有内容。

## Success criteria

- AC1：「交审要让用户看到内容」按上表列出五类审批的小项，名称与顺序与模板一致；回归按位置断言先后。
- AC2：内容不删：现有断言（范围内与范围外、关键决策与取舍、未决问题、验证方式、检查点及其类型、影响面、AC 编号、最终验收的
  三张表与文档单列）不改且全部通过，规则写明 AC 逐条全列、表格照旧。
- AC3：小项之后有独立的「注意：」与「批了会怎样：」两行；combined 写明 Spec 五项接 Plan 四项。
- AC4：卡住时交用户决定写「出了什么事」、各做法的代价与推荐，复制块规则同样适用。
- AC5：「交审时说明怎么批准」写明：每个选项选了会怎样（能不能撤回、还要不要另外问）、推荐理由、推荐答复放独立的可复制代码块
  且不用行内代码、不需要回答的内容不用代码块、“继续”不会被记为批准。
- AC6：`interface.json` 为 1.5，`reviewKinds` 正好七个契约代码，不含 `go-to-session` 与 `interface`；`check-interface.py` 对少一类、
  多一类、小项名在规则里找不到各报错，`test-checkers.sh` 有对应正反例。
- AC7：三处镜像（`commands/review-mark.md`、`skills/spec-guard-ops/SKILL.md`、`docs/commands.md`）与规则一致；约定块模板不变。
- AC8：类型代码与小项名与契约定稿一致；定稿前交最终验收时照实写「未对齐」。
- AC9：全套检查通过，插件版本号不变，CHANGELOG 只写「[未发布]」段。
