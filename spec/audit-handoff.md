# Spec: audit-handoff

## Objective

在 Spec Guard 的项目级审查中，给使用者一个有边界、可收束的审查批次，并在发现缺陷后接入现有事项和 agent-skills 修复流程。解决已分级的问题被反复“继续”带回无期限深挖、使用者不知道剩余步骤的体验。

登记：2026-10-02，Local 事项《审查批次收束与缺陷处理交接》（8C22GJK）；用户评审了解决方案并要求继续实施。能力图插入仍以 `module-insert.py` 的精确预览与确认为准。

## Assumptions

- 本模块面向跨文件或跨模块的项目级审查。单个 diff/PR 的批准判断继续使用 agent-skills 的 `code-review-and-quality`，不改其上游技能或命令。
- 审查完成表示约定范围已经检查且发现项已整理；不表示项目无缺陷、Critical 问题已解决或交付获批准。
- `Critical`、`Required`、`Optional` 等审查意见与 P0/P1/P2 处理优先级是不同维度，不能自动一一映射。
- 本次只增加交互约定、可恢复的审查报告格式和双宿主入口指引；不新增审查状态机、后台监控、网络写入适配器或 hook 写操作。

## Contract

### A1 有限审查批次

- 开始项目审查时写明基准提交或可识别快照、模块/路径范围、排除项和下一停点；有能力图的项目优先按现有模块划定范围。范围过大时拆批，不承诺一次穷尽整个仓库。
- 每个范围做一次系统检查。候选缺陷只做与结论有关的定向核实；已覆盖范围不因普通“继续”重新泛扫。证据仍不足时标为“待调查”，记录缺什么证据及获取方式，审查批次可以收束。
- 每个检查点报告已覆盖/总范围、待核实、已确认、待入账与下一步。所有预定范围完成、候选均已裁决为已确认/待调查/排除/重复时，明确宣布本批次审查完成。新证据或用户明确扩展范围时另开批次，保留原报告与基准。
- P0 或可能造成重大安全/数据损失的发现立即报告并暂停扩大扫描；记录尚未覆盖范围，先走紧急处置或等待用户对审查目的的决定，不把未扫范围说成已完成。

### A2 发现项与报告

- 多轮项目审查使用一份可恢复的报告，至少含批次身份、基准、范围、覆盖进度、发现项稳定编号、证据、审查结论、P 级优先级、状态、剩余风险和下一停点。报告可沿用项目现有 `docs/reports/` 或指定私有位置；写入仓库前检查敏感内容，不自动提交或发布。
- 一项根因对应一个可追踪发现。重复发现合并证据并保留来源；待调查项不得冒称已确认 bug；无发现时明确输出零发现与覆盖边界。
- 报告区分“审查完成”“事项已入账”“已修复待验证”“已交付并关闭”，不从 `phase` 的 `DONE` 或报告完成推断后续状态。

### A3 审查转事项

- 审查冻结后，普通“继续”承接最近预告的查重、入账、规划或修复步骤，不重新开启无界审查。仅用户明确要求新审查或发现新证据时才扩展。
- 对可执行缺陷先按根因查重。已启用且被选作事项来源的 Local 账本使用现有 `ticket` skill，复用其 `found`/`absent`/`unknown`、读回和关闭规则；Local 账本不可用或归属不明时保留“待入账”，不隐式安装或初始化。
- GitHub/GitLab 仓库中的 Local 事项仍以 Local 为准，沿用已存在的 PR 创建/合并后对账。仅 Git remote、旧 `.agent/state.json` 中的 tracker 字段或 Proposal Issue 不能推断日常缺陷事项目标。
- 对明确指定的 GitHub/GitLab 日常 Issue 目标，本模块只准备经查重的交接清单与可审阅内容，说明外部发布及读回尚需独立工作流和授权；不调用已退役 bridge、不执行或暗示 Spec Guard 自带远端 Issue 写入。若没有可用外部流程，保留“待外部交接”，不称已入账。
- 仅需修复现有行为的 bug 不强制新建能力模块。简单修复可从事项进入 agent-skills 的 debugging、TDD、review；需要多步骤实施时按当前项目约定维护对应模块的 plan/todo，不覆盖别的进行中工作。独立新能力再走 add-module 或 Proposal。

### A4 优先级、权限与停止

- P0 优先处置；P1/P2 按影响、依赖与可交付切片排序。审查证据和验收条件足够时进入修复，不以“也许还能找更多”阻断。
- 仅要求只读审查的用户收到报告和交接建议，不自动创建事项或改代码。明确要求处理问题且已有授权时继续；外部发布按具体目标与内容审阅，不用一个“继续”扩大授权。
- 写入结果未知先读回精确对象，不盲目重试；重复事项、离线/无认证、不同 worktree 并发、基准漂移均保留事实和未完成状态，不制造虚假的已入账或已关闭结论。

## Project structure

- `plugins/spec-guard/references/workflow-checkpoints.md`：单一共享审查交接规则。
- `plugins/spec-guard/templates/{claude,codex}-block-local.md`：使消费者在项目审查时发现规则。
- `plugins/spec-guard/skills/ticket/SKILL.md`：复用 Local 查重和入账，避免审查批量重复创建。
- `docs/workflow.md`：使用者路径与远端边界。
- `plugins/spec-guard/hooks/test_workflow_checkpoints.py` 等：契约与真实宿主验证入口。

## Verification

1. 静态契约测试检查双宿主模板、共享检查点、ticket 入口与文档彼此一致；审查冻结、P0、待调查、Local+GitHub PR 和未知 Tracker 的行为另以场景审阅。
2. 在隔离的临时消费者项目将候选约定注入真实宿主：给出已分级发现项后多次输入“继续”，记录其是否转入预告步骤，且未重复审查或建单。若无法安装候选插件或运行另一宿主，明确记录验证范围；静态文字测试不充当宿主验收。
3. 运行 `/bin/bash scripts/validate.sh`、`test-phase-guard.sh`、`test-verify-artifacts.sh`；检查退役 bridge 扫描仍通过，hooks 与 Proposal 行为不变。

## Boundaries

- Always：复用 agent-skills 审查/修复和 Spec Guard 现有 ticket、检查点、模块目录约定；报告未知事实；以已安装候选来源做宿主验证。
- Ask first：能力图精确插入预览；向第三方发布 Issue、PR 或审查内容；改变既有消费者约定块。
- Never：恢复旧远端 tracker bridge；把 Proposal Issue 当普通 bug Issue；用 `.agent/state.json` 记录审查阶段；由 hook 写入事项、报告或远端；覆盖现存进行中 plan/todo。

## Success criteria

- 审查批次有可见范围、进度和结束声明；已有 P0/P1/P2 结论时，“继续”沿已预告步骤进入问题处理，不能无理由扩大审查。
- Local、外部 Issue、无可用 Tracker 三种情况均准确报告实际完成与待办；Local+GitHub PR 合并继续沿用现有关闭对账。
- Claude 与 Codex 两端都能发现同一共享契约；回归及真实宿主证据分别报告，不混为一谈。
