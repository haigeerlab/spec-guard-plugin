# Spec: ui-verify-by-change

<!-- spec-guard: review pending -->

## Objective

spec-guard 是不分前后端的通用流程插件，但实际多用在带界面的项目上。改了界面不等于改对了：测试能证明逻辑对，证明不了按钮
在不在、样式有没有错位、页面有没有白屏。现有规则只有共享检查点规则里的「UI 自验」一节，查下来有六处漏洞：

1. **只在写 Plan 时判断一次“涉不涉及 UI”。** 做任务时才改到界面、Plan 没预料到的，没有任何一条规则要求验证。
2. **验证挂在检查点上，不挂在任务上。** Plan 只有最后一个检查点时，前面改界面的任务一路做下来都不看。
3. **没说验证什么。** 只说“用浏览器验证”，没说对照预期看改动处、看控制台报错，截一张图就可能算验证过。
4. **没说怎么打开页面。** 没说先启动开发服务、找到改动所在页面，找不到地址就容易跳过。
5. **做不了时没有明确的退路。** 没说无法验证时要如实记为“未验证”，不能说改好了。
6. **约定块里只有一个很弱的指向。** 模板只在讲检查点分级的那一行顺带提了“UI 自验按共享检查点规则”。

本模块改写「UI 自验」一节补上这六处，并在约定块模板里加一行。只改规则与模板文字，不加命令或钩子。

登记：2026-10-15 经 `/spec-guard:add-module` 插入能力图。需求来自用户，用户已确认方案。

## Assumptions

用户已于 2026-10-14 确认：

1. **按实际改动触发。** 任务做完时，由 agent 根据自己改了什么判断有没有改到用户看得到的界面；Plan 预计到、没预计到都一样。
   不靠文件后缀之类的规则判断，钩子也不判断。
2. **在任务里验证，不等检查点。** 改了界面的那个任务，验证步骤就包括打开页面看；检查点只汇总各任务的结果，不因此多停。
3. **怎么验**：启动项目的开发服务或打开构建产物，找到改动所在的页面；对照 Spec 或任务写的预期逐项看改动处；看控制台有没有
   报错。截几张图、测哪些尺寸等形式由 agent 按改动判断，不作规定。
4. **怎么报**：写清打开了哪个页面、对照了哪条预期、看到了什么；只写“已验证”不算。规则无法确认 agent 真的看了，所以靠
   报告内容让用户一眼看出。
5. **做不了时**：工具不可用、页面打不开或要登录、无人值守无法操作时，写“UI 未验证”并说明原因，不说已完成，不卡住流程。
6. **保留不变**：Plan 预计到时开头列出所需工具并提前提醒安装或授权；网页用浏览器工具（内置浏览器或用户已登录的 Chrome），
   原生界面经授权用电脑操作；AI 验证后人做最后兜底审查，这一步是 `gate`；Claude 桌面应用自身的显示只能由用户查看。
7. 不改变的项目：没改界面的任务、纯后端或纯命令行的项目不受影响。
8. 约定块模板只新增一行，已有的行（含“UI 自验按共享检查点规则”那一行）逐字不变。
9. 版本 0.60.3，本模块的 PR 带版本号；与已合并的 `doc-suggestion-template-line` 一起发。

## Contract

### 规则文本

`references/workflow-checkpoints.md` 的「UI 自验」一节改写为：

- 触发条件：任务改到用户看得到的界面（网页、原生界面、宿主如何呈现 hook 输出），不论 Plan 是否预计到。
- 按实际改动触发（Assumptions 1）；在任务里验证（Assumptions 2）；怎么验（Assumptions 3）；怎么报（Assumptions 4）；
  做不了时（Assumptions 5）；保留的四条（Assumptions 6）。

### 模板与文档

- 两份约定块模板在“模块最终验收时在对话里列出实际改动的文件”那一行之前各新增一行：
  ```text
  - 任务改到用户看得到的界面时，不论 Plan 是否预计到，都在这个任务里打开页面对照预期验证，写清看了哪个页面、对照了什么、
    看到了什么；做不了就记为“UI 未验证”并说明原因；细则见 `spec-guard:spec-guard-ops` 的共享检查点规则
  ```

## Testing strategy

- 先加断言并确认失败：`test_workflow_checkpoints.py` 的 UI 自验用例补关键词（不论 Plan 是否预计到、在任务里、开发服务、
  对照、控制台、看到了什么、UI 未验证），原有关键词（浏览器、电脑操作、缺失、提前提醒、兜底、Claude 桌面应用）保留；两份模板
  各含新行的关键词。
- `test-setup-teardown.sh` 全部通过。
- 发版后在两边宿主各用一个临时项目跑真实会话：项目里有一个静态页面，Plan 的任务是改页面上的一处文字，Plan 里不写 UI 验证，
  提示里也不提验证。看 agent 是否打开页面验证并写清看了什么；无人值守运行拿不到浏览器时，看它是否如实写“UI 未验证”及原因。
  同一次运行顺带看上一个模块的效果：能力图全部完成时是否给出收尾文档建议。

## Boundaries

- Always：规则只有一个出处；模板只新增行；保留现有四条。
- Ask first：让钩子判断是否改了界面；规定验证形式或指定唯一工具；把 UI 验证做成卡住流程的强制条件。
- Never：在 Spec、代码、测试、提交信息或 PR 中写入消费者项目的名称、模块或编号。

## Success criteria

- 「UI 自验」一节写明按实际改动触发、在任务里验证、怎么验、怎么报、做不了时怎么办，且保留现有四条。
- 两份模板各多一行，已有行逐字不变。
- 全套检查通过。
- 发版后的真实会话按 Testing strategy 观察，结果如实记录。
