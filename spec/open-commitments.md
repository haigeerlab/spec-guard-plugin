# Spec: open-commitments

<!-- spec-guard: review approved 21a7bdf1ac05 -->

## Objective

会话会被压缩、会被清空，这是常态。凡是会活过这一轮的东西，只放在会话上下文里就会丢。最容易丢的是**有人在等的事**：

- 别的会话、Issue 或邮件发来需求，当下正忙别的，没记下来；清空之后既不记得要做，也不记得该回给谁、从哪个通道回。
- 发了版、通知了对方，等对方升级后回报；对方不回，这边也没有任何地方记着“在等谁”。
- 有件事等用户拍板，只写在某一轮的回复里，压缩后就沉下去了。

0.63.1 的「需求来源与回告」管住了已建模块的来源记录与发版后回告，但三处仍只存在于会话里：建模块之前收到的需求、
回告之后的等待、等用户拍板的事；而且回复地址记的是会随会话结束而失效的会话 ID。

本模块把这三类合成一种记录——**未了的承诺**——并规定：

1. **球每换一次手就记一笔**，记在本地事项账本里，收到的那一刻就记，不等人提醒；
2. **新会话读得回来**：会话开始、清空与压缩后，注入一句提醒先查账本里未关闭的这类事项；
3. **回复按两道闸门**：会替用户做出承诺的先问用户，对外通道一律先给草稿；其余内部告知直接发。

没有外部来的事时，规则不触发，注入也只在启用了账本的项目里多一句。

登记：2026-10-18 经 `/spec-guard:add-module` 插入能力图。需求来自其他会话（依赖方插件的契约负责人会话，发件会话
`local_a9d06942-9b64-4887-b490-0088b10b8c75`，Claude 原生会话消息）代用户转达，用户在本会话（当前插件所有者）逐条梳理并确认；
本需求自身是第一条样例，记在本仓库账本。

## Assumptions

用户已于 2026-10-18 在本会话确认：

1. **一种记录统一三种情形**：别人在等我、我在等别人、在等用户，都是“未了的承诺”，区别只在“球在谁手里”。
2. **存在本地事项账本**，不另起文件，不给 Epiq 加功能；状态用标签表示，经过用评论记录。
3. **钩子不解析账本数据**：只判断项目根有没有 `.epiq/project.json`，实际查询由 agent 调账本自己的列表工具。
4. **默认通知后关闭**；只有确实有决定依赖对方采用（能否关事项、能否废弃旧版本、要不要保留兼容）时才等回报；
   等回报的追问一次，再不回记“未确认”并关闭，不再提醒，不挡任何工作。
5. **两道闸门**：会替用户做出承诺（答应日期、同意改接口、拒绝对方、扩大范围）的先问用户；对外通道（邮件、GitHub／GitLab
   评论、任何本机会话之外的地方）不论内容一律先在正文给草稿，用户答应才发；内部通道（宿主的会话消息、本机 agent-relay 信箱）
   上的告知直接发。改动本身的审批照旧。
6. **对方身份要稳定**：记项目加角色或 agent-relay 信箱名；会话 ID 只作最近联系的线索。
7. **隐私**：账本会推到公开远端时，记录里不写私有项目名与本机路径。本仓库的账本已改为纯本地（状态工作树单独配了必然失败的
   推送地址，2026-10-18，用户批准）。
8. **不做**：没启用账本的项目不另设退路，只提示可以启用；不读、不改其他插件的状态；核验对方升级时只核对对方附的证据，
   不去对方仓库重跑测试。
9. **一个模块、一个 PR、0.69.0**。

## Contract

### 一、记录：未了的承诺

一件有人在等的事是账本里的一个事项。标题写事项本身；正文写下面五项，经过每次换手追加一条评论。

| 字段 | 写什么 |
|---|---|
| 对方 | 稳定身份：项目加角色，或 agent-relay 信箱名；另记最近一次联系的会话 ID 作线索 |
| 来路与回路 | 从哪个通道来；回复走哪个通道、用哪个地址（默认原路回；对方指定过别的地址、原路已断或原路是公开通道而内容不宜公开时写明） |
| 内容 | 对方要什么，期待我回什么 |
| 关闭条件 | 做到什么算完：已回复、已交付并告知、或对方回报并核验 |
| 关联 | 对应的模块 id、Proposal、GitHub／GitLab Issue、版本号（有就写） |

“球在谁手里”用三个标签之一表示，同一时刻只挂一个：

- `waiting-on-me`：我欠对方一步（待回复、处理中、待核验）；
- `waiting-on-them`：我已发出，等对方（等回报、等对方交付）；
- `waiting-on-user`：等用户拍板或等用户同意发送对外草稿。

关闭时追加一条评论写结局：`已完成`、`已告知`、`已核验` 或 `未确认`（等回报追问后仍无回音），然后关闭事项。

### 二、写入规矩：球每换一次手就记一笔

写进 `references/workflow-checkpoints.md`，紧跟「需求来源与回告」之后新增一节「未了的承诺」：

- **收到**：会话、Issue、邮件发来对方期待回复或交付的消息，收到那一刻建事项（或给已有事项加评论），挂 `waiting-on-me`，
  再继续手头的事。不先判断“能不能马上做完”。只是寒暄、对方不期待任何回音的不建。
- **我回复或告知了**：评论记下发了什么、发到哪；不再欠对方什么且没有决定依赖对方采用时，按结局关闭；否则改挂 `waiting-on-them`。
- **我向别人提需求**：反方向的同一件事，建事项挂 `waiting-on-them`。
- **对方回报**：改挂 `waiting-on-me`，核对回报附的证据（提交号、版本、测试结果）是否自洽、与约定一致，然后关闭；不一致按
  「接收回告」处理。
- **等回报太久**：读回时发现 `waiting-on-them` 的事项上次联系已久，追问一次并评论记下追问日期；追问后再次读回仍无回音，
  记 `未确认` 并关闭。不设固定天数，不反复催，不挡工作。
- **要用户拍板**：改挂 `waiting-on-user`，把问题写在本轮正文里交给用户；用户答复后照答复处理并改回相应标签。
- **与已有规则的衔接**：0.63.1 的回告仍在最终 gate 列出、结果仍记在 todo 末项；本节只是把回告前后的等待也记进账本。
  建模块后，模块 Spec 的登记一句写明对应的事项短编号。
- **项目没启用账本**：不另找地方记；第一次遇到时告诉用户这件事不会落盘、可以用 `/spec-guard:local-ticket-ledger` 启用，
  不反复提。
- **隐私**：账本状态分支会推到公开远端时，“对方”只写信箱名或会话 ID，不写私有项目名、本机路径与消息原文。

### 三、读回入口：钩子

`phase-guard.sh` 只多一个判断：项目根（含经指向文件解析后的项目根）下是否存在 `.epiq/project.json`。不读 `.epiq` 下的其他文件，
不调用 Epiq，不启动额外进程。存在时：

- **会话开始与清空后**：`hooks.json` 新增一项 `SessionStart`，matcher `startup|clear`，调用 `phase-guard.sh SessionStart fresh`。
  这一项只输出一句读回提醒，不输出阶段摘要（阶段摘要由随后的 `UserPromptSubmit` 给；由其他会话的消息开启的会话也能看到这一句）。
  账本不存在或项目未激活时静默退出 0。
- **压缩后**：现有 `SessionStart`（matcher `compact`）注入的核对提醒，在“核对 todo 和状态记录”处补上“和账本里未关闭的
  `waiting-on-*` 事项”。账本不存在时这句话与 0.68.0 逐字节相同。
- 每轮 `UserPromptSubmit` 不变。

读回提醒（`artifactLanguage` 为 `zh-CN` 时用中文，否则英文，命令与标签名保持原样）：

> 本项目启用了本地事项账本：先列出带 `waiting-on-me`／`waiting-on-them`／`waiting-on-user` 标签的未关闭事项，`waiting-on-me`
> 的接着处理，`waiting-on-them` 的按需追问一次，`waiting-on-user` 的交给用户，再继续用户的请求；没有就直接继续。

Codex 与 Claude Code 的 `SessionStart` 都支持 `startup`、`clear` 来源（Codex 源码 `SessionStartSource`，matcher 为正则）；
构建时两边宿主各实测一次新会话与清空后的触发，结果记入 todo。Codex 按项记录 hook 信任，新的一项要用户单独信任一次，
在 CHANGELOG 与 README 写明。

### 四、两道闸门

同一节写明：

- **会不会替用户做出承诺**：答应日期或范围、同意改接口或契约、拒绝对方、接受对方的方案，先问用户；版本已发、怎么升级、
  核验结果这类告知，内部通道直接发。
- **对外通道一律先给草稿**：邮件、GitHub／GitLab 评论或 Issue、任何本机会话之外的地方。草稿写在本轮正文、在任何会结束本轮的
  确认框之前；最终 gate 已批准的拟回告，到发送时仍要再给一次草稿。
- 确实不知道怎么回（需求有歧义、超出权限）时问用户。
- 用户答应前事项挂 `waiting-on-user`。

### 五、约定块模板

`templates/claude-block-local.md` 与 `templates/codex-block-local.md` 各**新增**两行，现有行一字不改；`docs/convention-block.md` 同步：

> `waiting-on-me`／`waiting-on-them`／`waiting-on-user` 之一，写明对方的稳定身份与回复通道；细则见 `spec-guard:spec-guard-ops` 的共享检查点规则

> 回复会替用户做出承诺的先问用户；邮件、公开评论等对外通道一律先在正文给草稿，用户答应才发；内部会话间的告知直接发

## Testing strategy

- 先写断言并确认变红：
  - `test-phase-guard.sh`：`SessionStart fresh` 在有 `.epiq/project.json` 时只输出读回提醒（中、英各一例），没有账本或未激活时
    无输出、退出 0；`SessionStart`（压缩）有账本时核对提醒含账本一句，没有账本时与 0.68.0 逐字节相同；`UserPromptSubmit`
    有无账本输出相同；经指向文件解析的项目按目标项目根判断账本。
  - `hooks.json` 结构检查：三项都在，新一项 matcher 为 `startup|clear`、参数为 `SessionStart fresh`，兜底事件名与所在项一致。
  - `test_workflow_checkpoints.py`：新一节的关键词（收到那一刻、三个标签、稳定身份、会话 ID 只作线索、追问一次、未确认、
    不设固定天数、做出承诺、对外通道、草稿、没启用账本、隐私）；两份模板与 `docs/convention-block.md` 含新增两行。
- 其余回归不改，全部通过即证明原有行为未变；`setup-convention --replace` 在已有项目上不需要 `--accept-removals`。
- 发版后两边宿主各跑一次真实会话：临时项目启用账本，正在做一个小模块时由“另一个会话”发来一条需求，提示词里不提账本；
  观察 agent 是否当场建事项并写明对方与回复通道；随后清空会话，看新会话是否先查账本、找回该事项与回复对象；再让它回复，
  一次是内部告知、一次是需要答应日期，看是否分别直接发与先问用户。结果如实记录。

## Boundaries

- Always：钩子只判断文件是否存在，不读账本内容；没有账本时所有输出与 0.68.0 相同；模板只新增行；对外发送前给草稿；
  记录里只写事实，不贴消息原文。
- Ask first：钩子读取或解析账本数据；给“等回报”设固定天数或自动追问；为没启用账本的项目另设记录文件；改 Epiq 或其他插件。
- Never：替用户在对外通道发送；在公开远端的账本或本仓库文件、提交信息、PR 中写入其他私有项目的名称、模块、编号或本机路径；
  去对方仓库改文件或重跑测试作为核验。

## Success criteria

- 规则写明记录的五项与三个标签、每种换手的写法、追问一次后记未确认、两道闸门、没启用账本与隐私的处理。
- 两边宿主在启用账本的项目里，会话开始、清空、压缩后都能看到读回提醒；没有账本的项目输出与 0.68.0 相同。
- 两份模板与约定块文档各多两行，现有行不变；全套检查通过。
- 发版后的真实会话按 Testing strategy 观察，结果如实记录。
