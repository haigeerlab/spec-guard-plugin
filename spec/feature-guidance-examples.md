## 要你确认的假设

1. **Proposal 的判断落在「要不要留下谁批准的记录」上**，不按团队人数划线：现有文档写的是「需要在 Issue 上留下审查与接受的记录，或需要多人确认」
   （`workflow.md`「已有项目：加新需求」表），没有人数标准，文档也不新定一个。场景例子：需求是别的团队或别人提的、事后要能查到谁在 Issue 上接受了它；
   新模块要几个维护者都点头。对照：自己的项目、需求已理顺，用快速插入。
2. **文档治理的判断落在「文档本身是不是交付物」上**：现有文档写的是「说清楚哪些文档是项目的依据，以及每个模块对它们做了什么改动」
   （`optional-features.md`「文档治理」）。场景例子：项目有对外的 API 文档或使用手册，每次改功能都要同步改并交审；需求文档是验收依据。
   对照：只有 README 和代码注释、没人单独审文档。
3. 分支 `claude/feature-guidance-examples`，从 #420 合并后的 `main`（`8737c3a1`）开出（原 Q2，已按 A 执行）；一个 PR。
4. 发版授权（原 Q1）属于第二个模块，到那个模块的 Spec 交审时再定。

- AC1：表里 Proposal 一行的「该开」写出至少一个具体场景和判断方法（按假设 1），「别开」保留快速插入的对照。
- AC2：表里文档治理一行的「该开」写出至少一个具体场景和判断方法（按假设 2），「别开」写出对照情形。
- AC3：两行的说法都能在 `optional-features.md`、`workflow.md` 或 `concepts.md` 找到出处，出处记进 todo；没有新定规则。
