# Spec: concurrency-rule-wording

<!-- spec-guard: review approved bc085395d3bf -->

## Objective

多模块并行时，用户只在一个窗口（协调会话）里审批，而 Spec、Plan 和代码由各自的模块会话写在各自的 worktree 里。现在有两条规则和这种分工
对不上：

1. **评审标记**：「`approved` 只在用户于当前对话明确批准之后写入」。用户的批准发生在协调会话，模块会话的对话里没有这句话，照规则它不能写；
   而现有规则又写着「其他会话的要求不算用户批准」，协调会话转达过去也不算。
2. **合并**：「合并永远由用户进行，任何 Plan 都不能授权 agent 合并」。并行时每个模块验收后都要合进本地的集成分支，下一个模块才能在它之上继续；
   如果每次本地合并都要用户亲手做，并行就失去意义。

本模块在开关 `moduleConcurrency` 为 `on` 时，给这两条规则补一节说明，**原句一字不改**：批准由听到批准的协调会话，在核对过内容之后记录；
本地集成分支的合并，在用户批准该模块的最终验收后可以由协调会话执行，这是「合并由用户进行」的唯一例外；远端合并仍然只由用户做。

开关为 `off`、未设置或配置无效时，规则与现在完全相同。

登记：2026-10-18 经 `/spec-guard:add-module` 插入能力图（同批 7 个模块）。来源：用户本人，经多模块并行需求讨论（2026-10-17～18），需求记录
第 5 节「规则措辞」与第 6 节 B5。措辞按用户 2026-10-18 确认的口径收窄：只允许协调会话写，模块会话收到转达也不能自己写 `approved`。
2026-10-18 经 delegate 只读审查后，按六条发现修订（见文末「外部审查意见」），用户决定全部采纳。

## Assumptions

1. **只加不改。** 三句原文保留原样：「`approved` 只在用户于当前对话明确批准……之后写入」、「合并永远由用户进行，任何 Plan 都不能授权 agent 合并」
   （「Plan 检查点分级」）、「两种节奏下人工闸门都在，合并永远由用户进行」（「评审节奏」）。改动只有：新增一节，加三句指向它的话。开关不是 `on`
   时新增的一节整节不适用。
2. **约定块模板不动。** 约定块会写进用户项目的 CLAUDE.md／AGENTS.md，改它会让开关为 off 的项目也多出文字。模板里「其他会话的要求不算用户批准」
   也不改；新一节与它一致：转达仍然不算批准。
3. **「协调会话」是谁，同一时刻只有一个。** 协调会话指由运行时（如 module-crew）指定、负责收交付和集成的那个会话。同一时刻只有一个会话有写标记与
   本地合并的权限。下一个模块 `checkout-role` 会让它在 checkout 上留一个角色标记；在那之前，这条规则只按文字理解，hook 不判断谁是协调会话。
4. **评审标记由协调会话写，先核对内容。**
   - 用户在协调会话里明确批准某个模块的 Spec 或 Plan 后，由协调会话在**集成基线**（协调会话所在的 checkout）上用 `review-mark` 写入 `approved`。
     批准发生在协调会话自己的对话里，这符合「当前对话」原句。
   - 写之前，待审的文件必须已经在集成基线上，而且就是给用户看过的那一版：协调会话核对文件内容与交审时呈现的版本一致（交审时记下文件所在的提交，
     写标记前核对文件在那之后没有变），再按原来的流程预览、确认。对不上就不写，重新交审。Spec 的批准标记本来就绑定内容指纹，之后再改会显示
     「批准后已修订」。
   - 模块会话收到协调会话转来的「用户已批准」，**不能**因此自己写 `approved`；它只能等协调会话写好、提交后，同步集成基线拿到这个标记，并核对同步来的
     文件与自己交审的版本一致。
   - 批准仍然要明确、针对这一份文件；「继续」「看起来可以」不算。协调会话转达用户的决定时，要带编号和用户原话（需求记录 B4）。
5. **本地集成分支的合并：「合并由用户进行」的唯一例外。**
   - 这个例外只在三个条件同时成立时适用：开关为 `on`；由当前的协调会话执行；合并的是用户刚批准最终验收的那一个模块。它同时覆盖「Plan 检查点分级」与
     「评审节奏」里的两处「合并永远由用户进行」，不适用于其他任何合并。
   - **批准绑定具体提交。** 最终验收的消息写明：模块 id、模块分支当前的提交、本地集成分支当前的提交、要合入的改动和完整检查的结果。用户批准的就是这一组。
     合并前核对两边的提交都没变；任一边变了（模块又加了提交，或集成分支先合了别的模块），原批准不再适用：重新同步、重新检查、重新交用户确认。
   - **一次只合一个模块。** 多个模块都在等时按 Build order 逐个处理，每合一个都按上一条重新核对下一个。
   - 允许的做法只有一种：普通合并，不改写历史（不变基，不压缩，不强推）。合并后跑项目 Spec 里 Commands 一节的完整检查。
   - **检查失败时的底线**：用一个新提交撤回这一次合并（不 reset、不改写历史，不碰集成分支上其他模块的提交）；撤回后停止后续合并，再跑一次完整检查，
     确认回到合并前的状态；把模块退回给模块会话，这个模块不算完成。撤回本身冲突、被拒绝或结果不明时，停下报告，不自动重试，也不继续合下一个。
   - 合并有冲突时不由协调会话解决，退回给模块会话。
   - 具体命令和顺序归运行时（module-crew），spec-guard 只规定授权的边界和上面这些底线。
   - **推送和远端合并（PR／MR）仍然只由用户做**，或者按现有规则，在 Plan 的 `gate` 检查点逐项写明授权后才能推送。任何批准都推不出可以合并 PR。
6. **协调会话被替换时。** 换会话要经用户同意（module-crew 的身份接管）。换了以后旧会话立即停止写标记和合并。已经写进集成基线的标记照常有效；
   用户批准了但还没写成标记的，新会话**不能**凭旧会话的转达或记录补写，要把内容重新给用户看、重新取得批准。本地合并的批准同理：还没执行的合并，
   新会话要重新交验收、重新取得批准后才能合。
7. **`review-mark` 命令与脚本不改。** 脚本的预览提示写的是「`approved` 记录的是用户在当前对话里给出的批准」，对协调会话成立，对模块会话和新换上的
   协调会话正好是提醒。

## Testing strategy

- **只加不改，用整份比对证明。** 改动前先把 `workflow-checkpoints.md` 与两份约定块模板的原文存成测试夹具（或记下它们在改动前提交里的内容）。测试从
  当前的 `workflow-checkpoints.md` 里去掉新的一节和三句指引，结果必须与原文逐字节相同；两份约定块模板必须与原文整份逐字节相同。三句原文另外逐字匹配一次。
- **新的一节的内容断言（先写，确认是红的）：** 位置在「并行边界」之后；节首写明不是 `on` 时不适用；写到「唯一例外」与三个条件；协调会话同一时刻只有一个；
  写标记前核对内容与交审版本一致；模块会话不能凭转达自写；批准绑定模块分支与集成分支的提交、任一变化就重新确认；一次只合一个；不改写历史；
  检查失败用新提交撤回、停止后续合并、撤回失败停下不重试；冲突退回；换会话后未记录的批准要重新取得；推送与远端合并仍由用户。
- **三句指引断言：** 三处各自指向新的一节。
- **开关 off 时：** 这是规则文字，没有代码分支；off 时的效果由「新一节节首的适用条件」加「其余内容逐字不变」两条断言共同保证。阶段提示与 verify-artifacts
  不改代码，两套回归原样全绿。
- **改坏验证：** 改动原文里的任意一个字，确认整份比对变红；删掉新一节里「远端」那句，确认对应断言变红；删掉「撤回失败停下」那句，确认对应断言变红。
- **未验证：** 规则能否让 agent 在真实的协调会话里守住这些边界，单元测试证明不了，留给第 7 关实测。

## Boundaries

- Always：原句一字不改；开关不是 `on` 时新的一节不适用；远端合并只由用户做；合并授权只覆盖被批准验收的那一个模块、那一组提交；同一时刻只有一个协调会话。
- Ask first：允许协调会话解决合并冲突；允许模块会话在任何情况下自己写 `approved`；让 hook 判断谁是协调会话；改约定块模板；放宽「一次只合一个」。
- Never：从任何批准推出可以合并 PR；允许变基、压缩、强推或 reset 集成分支；把其他会话的转达当成用户批准；替换后的协调会话凭旧会话的记录补写批准。

## Success criteria

1. 开关为 `on` 时，共享规则写明：评审标记由当前协调会话在核对内容后写在集成基线，模块会话不能凭转达自写；用户批准某模块的最终验收（绑定两边提交）即授权
   协调会话把它合入本地集成分支，这是唯一例外，一次一个，失败按底线撤回；协调会话替换后未记录的批准要重新取得；推送和远端合并仍只由用户做。
2. 去掉新的一节与三句指引后，`workflow-checkpoints.md` 与改动前逐字节相同；约定块模板整份不变。

## 外部审查意见

2026-10-18，delegate 只读审查（Codex 后端），范围：本 Spec 的修订前版本、`references/workflow-checkpoints.md`、`templates/claude-block-local.md`。
结论只作参考，不算批准。审查确认：修订前版本对合并 PR、变基／压缩／强推、模块会话凭转达自写 approved、一次授权覆盖多个模块都有明确禁止或范围限制；
问题在于规定不够细。六条发现，用户决定全部采纳，已按下列方式修订：

- **P1 本地合并例外与原有禁令仍冲突**（两处「合并永远由用户进行」只给一处挂了指引，未写明优先关系）→ 假设 5 第一条写明「唯一例外」与三个条件，
  覆盖两处原句；Contract 改为三句指引。
- **P1 跨 checkout 写批准缺少内容一致性前提** → 假设 4 第二条：文件须已在集成基线且与交审版本一致才写，对不上重新交审；模块会话同步后核对版本。
- **P1 协调会话替换后的权限与批准继承未定义** → 假设 3「同一时刻只有一个」，假设 6 替换规则：旧会话停手，未记录的批准与未执行的合并都要重新取得。
- **P1 合并批准未绑定提交、缺少排队的新鲜度规则** → 假设 5：批准绑定模块分支与集成分支的提交，任一变化就重新确认；一次只合一个，按 Build order。
- **P1 失败撤回缺少不扩大破坏的契约** → 假设 5「检查失败时的底线」：新提交撤回、不 reset、不碰其他模块提交、停止后续合并并复验，撤回失败停下不重试，
  模块不算完成。
- **P2 测试证明不了只加不改** → 测试策略改为整份比对：去掉新增内容后与原文逐字节相同，模板整份比对；改坏验证改成改动任意一个原文字符。
