# Spec: scope-authorization

<!-- spec-guard: review approved a0ed63208b5a -->

## Objective

一个真实的前端项目里，一个模块卡在同一个检查点上近 12 小时、问了用户 20 次，每次只要一个很小的许可（装一个包、联网一次）。
根因之一是授权按次给、不按范围给：Plan 批了，装 Plan 要用的依赖仍被当成新的许可来问。spec-guard 的规则写了「已有授权涵盖时
无需确认」，却没写明**批 Plan 到底涵盖什么**，也没让 Plan 把要用的外部条件列出来，agent 只能保守地逐次去问。

本模块只改规则文字，加一条 verify-artifacts 提示，让「批 Plan」成为一次按范围的授权：

- 批 Plan 即授权 Plan 列出的外部条件和范围内的常规操作，按范围、不按次数；
- Plan 开头写一节「需要的外部条件」；
- 只在明确的几类情况停下问用户；
- 同一目标第二次报批时，可以一次列全所需权限；
- 最终验收列出新增依赖与锁文件改动；
- 停在宿主确认（弹窗、提权）前，告诉用户去哪个会话、点什么。

spec-guard 看不到问了用户几次，也不判断打转；这些归读取方。规则只管 agent 什么时候该问、什么时候不该问。

登记：2026-10-19 经 `/spec-guard:add-module` 插入能力图，依赖 `checkpoint-tiers`、`stop-rule-and-ac`、`changed-files-at-acceptance`。
需求来自接入协调人转达的 R21 条目 SG-1、SG-2、SG-3、SG-4、SG-5、SG-6、SG-8（用户决定 58–61）；用户在本会话同意 SG-2、SG-3、
SG-6 按负责人的调整做，SG-5b（依赖清单核对）拆到下一个模块 `dependency-check`，两个模块一起发 0.78.0。

## Assumptions

1. **批 Plan 授权什么（SG-1、SG-3）**：Plan「需要的外部条件」一节列出的每一项（装哪些依赖、访问哪些官方源、用哪些工具），以及
   范围内的常规操作——改本仓库文件、跑测试与构建、本地提交。授权按范围算、不按次数消耗：同一项用第二次、第三次都不再问。
   `gate` 检查点和远端写入（推送、开 PR、建 tag）照旧按现有规则，不因本条免问。规则只说 agent 该不该问用户；宿主自己的确认
   （弹窗、沙箱）不受规则控制，见第 6 条。
2. **「需要的外部条件」一节（SG-2）**：写在 Plan 开头，列要装的依赖（有版本要求就写）、要联网访问的官方源、要用的工具；事先列
   不全的探索类模块可以写一条「允许范围」，例如「为跑通 X，可以从官方源装开发依赖」。没有就写「无」。现有「Plan 开头列出验证
   所需的工具」（UI 自验）并入这一节。标题或行首写作 `需要的外部条件`（英文 `Required external conditions`）。
3. **verify-artifacts 只提示（SG-2）**：对能力图里阶段不是 `DONE`、且已有 `tasks/<id>/plan.md` 的模块，Plan 里既没有这样一个标题、
   也没有以它开头的一行时，给一条 `⚠️` 提示，不让 verify-artifacts 失败；已完成模块不追溯。判定方式与 AC 编号检查同一段落风格
   （跳过代码块），python3 不可用或读不出时给「未验证」。
4. **只在这几类情况停下问用户（SG-4）**：现有「异常停点」改写为一张完整清单——`gate` 检查点；远端写入；改模块范围；Spec 没覆盖
   的决定；Plan 没列的新依赖；不可逆或高风险操作（推送、发布、删除工作区外的文件、改全局配置、外发凭据）；测试改不红，或失败
   无法用测试证明原因；权限被拒；结果未知；同一目标第二次过不去或第二次报批。清单之外的范围内操作直接做，不为「是否继续」发问。
5. **Plan 没列的新依赖只问一次**：用户同意后，把它补进 Plan 的「需要的外部条件」，在 Plan 末尾「变更记录」追加一行（已有规则），
   之后同一项不再问。用户拒绝就按「权限被拒」处理。
6. **宿主确认（SG-8 与决定 61 的补充）**：停在宿主的确认（权限弹窗、提权申请、沙箱拒绝后要重试）前，告诉用户去哪个会话、点什么、
   为什么要点；这不算问用户做决定，也不算对同一目标的报批。宿主按命令前缀放行、分不出包在不在 Plan 里，所以往项目里加新包时
   宿主仍可能要用户点一次：建议模块开工时用一条命令把 Plan 列出的包一次加完，让这一下只出现一次。规则不引用任何收件枢纽的格式，
   没装别的插件也适用。
7. **同一目标第二次报批（SG-6）**：现有的三个选项（挂起并先开可开工模块、接受风险、换方案）保留，新增第四个——一次列全过这个
   检查点所需的全部权限，打包问一次。不缩成二选一。
8. **最终验收列出依赖改动（SG-5）**：在现有「实际改动的文件」清单里加一行：本模块新增或升级的依赖（取自依赖清单的差异，不凭记忆）
   与锁文件有没有改动；都没有写「无」。逐项和 Plan 对照的自动核对归下一个模块 `dependency-check`。
9. **改哪些地方**：共享检查点规则 `references/workflow-checkpoints.md`；约定块两份模板、`docs/convention-block.md` 与本仓库
   `AGENTS.md` 的约定块同步（`validate.sh` 的一致性检查照旧要过）；`verify-artifacts.sh` 加一段提示与两边回归。`phase-guard.sh`
   与每轮注入不变。
10. **不改版本号**：本模块不单独发版；版本号、CHANGELOG 的 `[0.78.0]` 一节由 `dependency-check` 的 PR 写，覆盖两个模块。

## Contract

### 共享检查点规则 `references/workflow-checkpoints.md`

- 「Plan 检查点分级」加两条：
  - **批 Plan 按范围授权**：第 1 条的内容；
  - **Plan 开头写「需要的外部条件」**：第 2 条的内容，写明 verify-artifacts 只对未完成模块提示。
- 「异常停点」一条改写为第 4 条的完整清单；新增「Plan 没列的新依赖只问一次」（第 5 条）。
- 「同一模块、同一目标第二次过不去」一条的选项加第 7 条的第四项。
- 「最终验收列出实际改动的文件」一条加第 8 条那一行。
- 「UI 自验」的「Plan 开头列出验证所需的工具」改为写进「需要的外部条件」一节。
- 「权限、未知结果与取消」加一条「宿主确认」（第 6 条）。

### 约定块（两份模板、`docs/convention-block.md`、本仓库 `AGENTS.md`）

- 新增一行：批 Plan 即按范围授权 Plan「需要的外部条件」与范围内常规操作，不按次数；Plan 开头写这一节，没有写「无」；细则指向
  共享检查点规则。
- 外部阻塞那一行的选项里加「一次列全所需权限」。
- 最终验收那一行加「新增依赖与锁文件改动」。
- 新增一行：停在宿主确认前告诉用户去哪个会话、点什么，这不算问用户做决定。
- 只问用户的完整清单不进约定块（太长），约定块指向共享检查点规则。

### `hooks/verify-artifacts.sh`

- 新增一段：按第 3 条找未完成且有 Plan 的模块，缺这一节时
  `warn "<id> 的 Plan 没有「需要的外部条件」一节；批 Plan 按这一节授权，没有就写「无」"`；读不出时 `warn "未验证：…"`。
- 不加 `ok` 行；不改其他检查与退出码。

### 不变

- `phase-guard.sh` 与每轮注入逐字不变；检查点未标注仍按 `gate`；远端写入与合并的规则不变；`module-suspend`、`/map` 不变。

## Commands

```bash
/bin/bash scripts/validate.sh
/bin/bash plugins/spec-guard/hooks/test-phase-guard.sh
/bin/bash plugins/spec-guard/hooks/test-verify-artifacts.sh
python3 -B plugins/spec-guard/hooks/test_workflow_checkpoints.py
```

## Testing strategy

- `test-verify-artifacts.sh`：未完成模块的 Plan 缺这一节 → 出提示；写成标题、写成行首「需要的外部条件：无」、英文标题三种都不提示；
  只在代码块里出现 → 仍提示；模块已完成 → 不提示；还没有 Plan → 不提示；提示不改变退出码。
- `test_workflow_checkpoints.py`：断言共享检查点规则里出现第 1、2、4、5、6、7、8 条的关键句（按范围不按次数、需要的外部条件、
  只问一次、宿主确认不算报批、一次列全所需权限、新增依赖与锁文件）；约定块模板含新增的两行与两处修改。
- 反向：故意删掉其中一句，对应断言变红。

## Boundaries

- **会做**：规则文字、约定块同步、verify-artifacts 的一条提示与回归。
- **先问**：让 verify-artifacts 因缺这一节而失败；把规则放进每轮注入；替用户改宿主配置。
- **不做**：数问用户的次数、判断打转；解析依赖清单（归 `dependency-check`）；引用收件枢纽或别的插件的消息格式。

## Success criteria

- AC1：共享检查点规则写明批 Plan 按范围授权「需要的外部条件」与范围内常规操作、不按次数，`gate` 与远端写入照旧。
- AC2：规则与约定块要求 Plan 开头写「需要的外部条件」（可写允许范围，没有写「无」），UI 自验的工具清单并入这一节。
- AC3：verify-artifacts 对未完成、已有 Plan 且缺这一节的模块给提示、不失败；三种合法写法、已完成或没有 Plan 的模块都不提示。
- AC4：「只问用户」的完整清单取代原「异常停点」，含 Plan 没列的新依赖只问一次及之后补进 Plan 的做法。
- AC5：同一目标第二次报批的选项保留原三项，并新增「一次列全所需权限」。
- AC6：最终验收的改动清单多一行新增依赖与锁文件改动。
- AC7：宿主确认一条写明去哪个会话、点什么，不算问用户决定，并建议开工时一条命令装完 Plan 列出的包。
- AC8：四处约定块一致，`validate.sh`、两边回归与 `test_workflow_checkpoints.py` 通过；`phase-guard.sh` 输出不变。
