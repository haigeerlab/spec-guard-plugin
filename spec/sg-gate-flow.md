## 目标

自动驾驶第一版的模块 4「关卡流程」。现在 spec-guard 的关卡是按「每一步都由人批」写的：合并永远由用户在对话里决定，里程碑做完一定停下，发版每次都先问。
自动驾驶第一版要把停点收到需求 R1 的四个关卡（需求确认、能力图、总体技术方案、发版确认），其余交给 autopilot（hub）自动做；这件事里属于 spec-guard 的部分由本模块完成：

1. 需求确认时问「做完自动发版吗？」，把答复记成提前授权，交给 hub 读；
2. 新增「总体技术方案」这一关；
3. 里程碑停点在 `autopilot` 档下改成不阻塞的汇报；
4. 共享检查点规则里的合并写法改成「交给 autopilot／由用户决定」两种情况，并补上「出事处理」一节；
5. 新增 `autopilot` 关卡预设和单项覆盖；
6. 会话自己连着做几步之前先说一句。

依据：自动驾驶第一版的需求文档（R1、R2、R5、R6、R9、S1、S2、S15、S17）、能力图第 4 行、总体技术方案第 6、7、8 节与 4.8（均已由用户批准），

## 给谁用

## 使用场景

1. **`autopilot` 档的项目提一个新需求**：复述需求时 agent 问「做完自动发版吗？」；用户答「是」，需求文档头部写 `<!-- spec-guard: release-preauth yes -->`，用户确认后记批准；
   之后需求文档被改动，批准指纹失效，提前授权随之失效。hub 在发版前读 `/map --json` 的 `releasePreauth`，是 `true` 才按提前授权走。
2. **`none` 档的项目提一个新需求**：和现在一样，不问发版，需求文档没有这一行，`releasePreauth` 为 `null`。
3. **全新项目或全新模块**：复述需求时 agent 提出「这次要总体技术方案」，用户确认需求时一并确认；能力图批准之后、第一个模块开工之前，阶段提示要求写总体技术方案并交用户批，批了才往下。
4. **`autopilot` 档的里程碑做完**：阶段提示与 `/map --json` 报「里程碑 M<n> 已完成，未确认」，并说明不阻塞；流程接着开下一个模块，用户事后仍可用 `milestone-mark` 写确认记录。`none`、`merge` 档照旧停下等用户判定。
5. **新流程模块开 PR 之后**：属于「交给 autopilot」的情况（新流程模块、生效档位合并是 `auto`、所在仓库长期授权写的其余条件都满足）时交给 hub，不问用户合并；其余情况照旧由用户在对话里说「合并」。
6. **构建中出了事**：验证没过、审查有阻断、测试失败时，会话按「出事处理」一节修或停。
7. **用户想个性化关卡**：配置写 `{"preset":"autopilot","release":"human"}`，其余项取 `autopilot` 的值；`/map --json` 的 `takeover.preset` 给出生效的预设名。
8. **会话要自己连着做几步**（写技术方案 → 回归文档 → Plan → 实现）：开始前先用一句话告诉用户接下来要做什么，再做。

## 业务规则和异常情形

**提前授权（R5）**

1. 「档位允许自动发版」指本模块生效档位的 `release` 是 `auto-confirm` 或 `auto`。只在允许时，需求确认的复述里加一问「做完自动发版吗？」；不允许时不问，需求文档不写这一行。
2. 用户答「是」才写 `<!-- spec-guard: release-preauth yes -->`，答「否」不写这一行。这一行写在需求文档头部、流程标记行附近，属于批准指纹的范围：需求批准后这一行或文档被改，批准失效，提前授权随之失效。
3. `/map --json` 每个模块的 `takeover` 加 `releasePreauth`：
   - `true`：新流程模块，需求文档有这一行，需求已批准且指纹有效，生效档位允许自动发版；
   - `false`：档位允许自动发版，但需求文档没有这一行（用户答了「否」），或者批准不成立；
   - `null`：老流程模块，或者档位不允许自动发版。
4. 作废条件（改到 T4、要升主版本号）由 hub 在发版前判定，spec-guard 不判、不写回文件。
5. 提前授权只用于发版；第一版不给别的关卡用，但标记的写法留出扩展余地。

**总体技术方案关卡（R1）**

6. 需求复述时由 agent 提出这次要不要总体技术方案，用户确认需求时一并确认。项目还没有任何代码时默认提出「要」。
7. 要的话，整个需求共用一份总体技术方案文件，放在 `spec/` 下；这个需求的每个模块，在流程标记行里写明它属于哪一份总体技术方案（同一需求的模块指向同一个文件）。
   不要的需求，流程标记行不写这一项，行为和现在相同。标记的具体写法与文件命名在本模块的技术方案里定，阶段提示和 verify-artifacts 都按它判定。
8. 总体技术方案的批准沿用批准标记（文件里一行 `review pending|approved`，带指纹），只由用户批：接管档位不能代替，Codex 的批准也不算。
   能力图批准之后，指向它的模块在总体技术方案批准（且指纹有效）之前，阶段提示停在「总体技术方案」这一关，不往下写模块技术方案、回归文档、Plan；文件缺失、标记缺失或指纹失效都算没批。

**里程碑（R2）**

9. 「生效预设是 `autopilot`」指 `/map --json` 里这个模块的 `takeover.preset` 是 `autopilot`：直接写 `autopilot`，或者带 `"preset":"autopilot"` 的单项覆盖对象都算（不论覆盖了哪几项）。
   这时里程碑停点不阻塞：阶段提示照报事实，不要求先停下；`/map --json` 的 `milestoneStop` 照样给出，并加一个字段 `blocking: false`，module-crew 据此不停。其余情况 `blocking: true`。
10. `none`、`merge` 档和不带 `preset` 的自定义对象，行为和现在逐字相同（`milestoneStop` 只多一个 `blocking: true`）。`milestone-mark` 保留。
11. 「生效预设」按本模块自己的生效档位算。并行推进时，几个模块档位不同，只要有一个在停点上的模块不是 `autopilot`，就照旧停。

**合并写法（③-2）**

12. `references/workflow-checkpoints.md` 第 162～163、165、180、331、520～522、542 行六处，逐字换成模块 1 草稿 ③-2 用户已批的措辞。
    原文来源：插件生态总账（`plugin-ecosystem` 仓库）`research/2026-11-26-自动驾驶目标/模块1-环境与授权-草稿.md` 的「③-2」一节，获批提交 `cae816e`（用户「批准，D1、D2 按推荐」）；
    到 `7b2daf7` 为止这一节没有改过。技术方案附上六处改后的全文，实现照技术方案里的全文替换，逐字比对以它为准。
13. 回归测试里钉着旧原文的地方随之改成钉新原文（`hooks/test_workflow_checkpoints.py` 八处），不删断言。
14. 「合并永远由用户在对话里决定」这句话不再出现在规则里；两份约定块模板和其他引用这句话的地方一起核对。

**出事处理（R6，只写会话的规矩）**

15. `workflow-checkpoints.md` 新增「出事处理」一节，适用所有档位，管的是**开 PR 以后**（以及合进主干、发版以后）出的事；构建中本地写代码时测试没过、写错了，照现有规则（第 154 行「agent 自己能修的失败不算，照旧自己修」）自己修，不计次数。两条规则各管一段，现有那一句补一个指向本节的说明。
    - 能修的：PR 上测试暴露的代码问题、合并前验证没过、审查有阻断。先找根因再修，同一个原因最多修两次，还不行就停下，说明出了什么事、试过什么、可选的做法和各自的代价。
      同一项检查、同一条回归用例或同一条审查意见失败，算同一个原因；改了代码以后重新跑一遍失败的那项检查，算修一次。
    - 修的过程中不改已有的测试和回归用例，要改就停下找用户；实现新功能时新写测试不受这条限制。
    - 测试失败时，可以分析是代码的问题还是用例的问题，写明依据，但不自己下结论放行；判断为用例的问题时，停下交用户。
    - 合进主干后 CI 变红、已发布的版本有问题：不自动撤回，通知用户，由用户决定。
    - 任何一步等了明显超过平常的时间还没结果，停下告诉用户，不空等、不跳过。参考时长：PR 的 CI 或打开自动合并后 60 分钟、发布的单个步骤 30 分钟（总体技术方案第 6 节的值）；
      其他步骤没有固定时长，由 agent 按这一步平常要多久判断，停下时写明等了多久、平常多久、依据是什么。
    - CI 变红的分类、自动重跑与收紧档位由 autopilot 做，这里只写一句指过去；没装 autopilot 时，CI 变红按「能修的」处理或交用户。
16. 这一节的措辞随本需求文档交用户批，批准后才写进文件。

**关卡预设（R9）**

17. 新增预设 `autopilot`：`design` 是 `reviewer`，`merge` 是 `auto`，`release` 是 `auto-confirm`（允许提前授权；没有提前授权时 hub 按 `prepare` 跑）。
18. 出厂默认仍是 `none`。`autopilot` 只在配置里写明（项目 `takeover`、模块 `moduleTakeover`，或经 setup 写进配置）时生效。
19. 单项覆盖沿用现有的对象写法，并允许带 `preset` 键：`{"preset":"autopilot","release":"human"}`，对象里没写的项取该预设的值。不带 `preset` 的对象照旧：没写的项按 `human` 读。
20. 优先级不变：模块的 `moduleTakeover` > 项目的 `takeover` > 默认；收窄记录总是往严里压。收窄的阶梯在 `merge` 之上加一格 `autopilot`。
21. `/map --json` 的 `takeover` 加 `preset`：生效的预设名；自定义对象不带 `preset` 时为 `null`。
22. 需求确认、能力图、总体技术方案三关永远由用户批，不在预设里，也不能用单项覆盖改。
23. 改档位、预设仍然只认用户在对话里的原话，`/spec-guard:config` 的写入规矩不变。

**先说一句（4.8）**

    只是一句汇报，不是停点，不等用户回答。逐个关卡点名该用哪个 skill 归模块 7，本模块不做。
