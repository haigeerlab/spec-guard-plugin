# Spec: acceptance-review-streamline

## Objective

一份真实使用报告（全新项目，9 个模块，用户介入约 55 次）和随后的补充报告，指出交审环节有三处问题：

1. **O2 最终验收前多一轮 Spec 复审。** 每个模块做到最终 gate 时，都发现实现比 Spec 多出几处接口要补进 Spec。Spec 批准后被改
   就得复审，于是每个模块都多一轮“批准修订后的 Spec”，9 个模块次次如此。
2. **O2b 验收后多停一次。** 每个模块验收后，会话都停下来问“开始写下一个模块的 Spec 吗？”，共 8 次。规则并没有要求这一停，
   下一份 Spec 写完本来就要交审。
3. **O4 交审内容没进对话（已造成误导）。** 三个不同的会话都把要审的东西只放进桌面版确认框的一句摘要里，对话正文没有内容，用户
   无从审起。现行规则已写“只给一句概述不算交审”，但没点明“确认框会结束本轮，内容必须写在它之前”这个坑。

另顺带更正 `docs/design.md` 一处过时的说法：“插件不记录原因或日期”。现在挂起可以用 `--reason` 记一行原因，挂起时长由进度表
从 git 历史读出。

登记：2026-10-16 经 `/spec-guard:add-module` 插入能力图。需求来自会话「Spec/Guard 插件使用观测」（`local_3b05d344-963e-4750-8edb-83b08ad9d0ca`）
的两份报告，经用户审阅后转来；用户 2026-10-16 决定做 O2、O2b、O4，O5–O8 只作记录。发版后按「需求来源与回告」回告该会话。

## Assumptions

用户已于 2026-10-16 在能力图预览时确认：

1. **只改规则文字与文档**：改 `references/workflow-checkpoints.md` 与 `docs/design.md`、`docs/workflow.md`；不加命令、钩子或
   检查，不改约定块模板（模板已有“在对话里呈现内容要点，只给链接不算交审”，指向这份规则）。规则在插件包里，所以发 0.63.3。
2. **O2 只合并验收那一刻的两次批准。** 条件：Spec 的改动差异原样贴在验收消息里（新增与删除的行，或改前改后对照），并写明
   一次批准同时算验收与 Spec 复审。用户批准后，agent 先用 `review-mark` 记下 Spec 的批准，再做其他事。构建途中改 Spec、且改动
   会影响后面的任务时，照旧当场停下复审（异常停点“Spec 没覆盖的决策”不变）。
3. **O2b 只在两个条件都满足时适用**：下一个模块已在能力图里；用户没说要停。验收消息预告一句“批准后接着写 X 的 Spec；要先压缩
   就先发 /compact”，批准后直接写，写完照常交审。下一个模块还要新插入能力图时，照旧先给用户看新行。
4. **O4 不点宿主的按钮名**，写成“任何会结束本轮的确认框”：要审的要点写在本轮正文里、在这类确认框之前；只出现在确认框摘要里
   的不算交审。

## Contract

规则文件 `references/workflow-checkpoints.md` 的三处改动（文字以实现为准，下面是必须表达的意思）：

**「Plan 检查点分级」新增一条：最终验收附上 Spec 的改动**

- 构建中补改了已批准的 Spec（阶段提示会报“批准后已修订”）时，最终 gate 的验收消息除现有内容外，原样附上 Spec 的改动差异，
  并写明“批准本次验收即同时批准修订后的 Spec”。
- 用户批准后，第一个动作是用 `review-mark` 记下 Spec 的批准，然后才是勾选与提交。
- 没附差异、或只给一句概述时，验收批准不算 Spec 复审，Spec 仍按「评审状态标记」单独复审。
- 构建途中的修改若会改变后续任务的做法，照旧当场停下复审，不留到验收。

**「阶段交接」新增一条：验收后接着写下一份 Spec**

- 最终 gate 获批后，下一个模块已在能力图里、用户没说要停时，直接开始写它的 Spec，不为“是否开始”另停一次。
- 验收消息里预告这一步，并提示要先释放上下文的话先发 `/compact`。
- 下一个模块需要新插入能力图时不适用，照旧先给用户看新行。

**「评审状态标记」的「交审要让用户看到内容」补一句**

- 要审的要点必须写在本轮的对话正文里，放在任何会结束本轮的确认框（例如宿主的“下一步”框）之前；只出现在确认框摘要里的
  不算交审，这样得到的批准不记为 `approved`。

文档：

- `docs/workflow.md` 的相应说明同步这三点。
- `docs/design.md` 把“插件不记录原因或日期”改为：可用 `--reason` 记一行原因；挂起时长不另存，由进度表从 git 历史读出。

## Testing strategy

- `test_workflow_checkpoints.py` 先加断言（三处新文字的关键词各在对应小节里），先红再补规则转绿。
- 现有断言不改；约定块模板不变，`setup-convention --replace` 不受影响。
- 发版后：两边宿主各一次真实会话，做到某个模块的最终 gate，看验收消息是否附上 Spec 差异并说明一次批准、批准后是否接着写
  下一份 Spec；交审时要点是否出现在正文里。

## Boundaries

- Always：规则只有一处出处；O2 的合并以“差异已原样呈现”为前提；记批准仍经 `review-mark`。
- Ask first：给钩子或 `verify-artifacts` 加检查；改约定块模板；把 O2 扩大到验收以外的时刻。
- Never：在仓库、提交或 PR 里写消费者项目的名称或路径；让含糊的答复记为批准。

## Success criteria

1. 规则写明验收附上 Spec 差异即可一次批准、批准后先记标记；没附差异不算复审；途中会影响后续任务的修改照旧当场停。
2. 规则写明验收获批后接着写下一份已在能力图里的 Spec，不另停；验收消息预告并提示 `/compact`。
3. 规则写明要点必须在正文、在会结束本轮的确认框之前，只在确认框摘要里的不算交审。
4. `docs/design.md` 的挂起说法与现行行为一致；`docs/workflow.md` 同步。
5. `test_workflow_checkpoints.py` 与 `validate.sh` 全绿；发版后两边真实会话按 Testing strategy 观察并如实记录，回告观测会话。
