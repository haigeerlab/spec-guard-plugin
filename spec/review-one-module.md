# Spec: review-one-module

<!-- spec-guard: review approved 032eca2de136 -->

## Objective

2026-10-18，agent 在串行开发时把两个模块合在一起交审：先列两份 Spec，再列两份 Plan，构建时却是一个接一个做。用户的反馈是：

- 实现是按顺序做的，合在一起审没有任何好处，只会让人看不清；两个模块关联不强时更乱。
- 给人看的顺序要一个模块一个模块地出现：先完整呈现模块一（Spec → Plan → 任务），审完再呈现模块二。
- 就算开了多模块并行、确实要几个模块一起审，也要按模块分组，不能排成「Spec 一、Spec 二、Spec 三，然后 Plan 一、Plan 二、Plan 三」。

现行规则里有两处会让 agent 主动合并交审：「按需求批量前置审」写的是「用户可以一次审完」，没有说必须由用户提出；「返工与小模块」写的是
小模块「确需各自成模块时，用『按需求批量前置审』一次交审」，读起来像 agent 可以自己决定。这次 agent 还把「一起发一个版本」误当成了
「一起审」。另外，规则写了交审要呈现哪些要点，却没有写几个模块同时出现时怎么排。

本模块把「一次只交一个模块」和「几个模块一起审时按模块分组」写进共享检查点规则和约定块，并收紧这两处写法。

登记：2026-10-18 经 `/spec-guard:add-module --interrupt` 插入能力图（`review-marker-blank-line` 只剩发版后的验证）。来源：用户本人，在本会话
（当前插件所有者）提出。并行模式下协调会话的汇总正文由 module-crew 生成，同一要求已作为需求发给 module-crew 的负责人（本仓库账本事项 Z2SZX42）。

## Assumptions

用户已于 2026-10-18 确认前两条，其余是本 Spec 的设计取舍，随本 Spec 一并审：

1. **默认一次只交一个模块。** 一个模块的 Spec 审完、Plan 审完、构建、验收、开 PR，然后才写下一个模块的 Spec。几个模块要合发一个版本时也一样。
2. **几个模块一起审只有两种情形**，而且都按模块分组呈现：
   - 串行时，用户本人明确要求一次审完同一需求拆出的几个模块（「按需求批量前置审」）；
   - 开关 `moduleConcurrency` 为 `on` 时，协调会话汇总几个模块会话的交审。
3. **agent 不主动提议合并交审。** 不问「要不要一起审」，以免把收紧变成多一次打扰。
4. **分组的写法**：每个模块一节，节标题写模块 id；节内依次是 Spec 要点、Plan 要点（有的话）、任务；多个模块按 Build order 排；跨模块的接口和
   依赖提示写在各自模块那一节里，汇总的冲突提示放在最后。
5. **能力图评审不受影响。** 能力图评审本来就要一次看全所有模块的拆分，这不算合并交审。
6. **只改文字。** 不加钩子判断、不加检查；`combined` 节奏（同一个模块的 Spec 与 Plan 一次审）不变。
7. **版本 0.70.2。** 0.70.1 已合并、还没打 tag，先按原计划发 0.70.1，本模块随后单独发 0.70.2；一个 PR。

## Contract

### 一、共享检查点规则

`references/workflow-checkpoints.md`：

- 「评审状态标记」一节的「交审要让用户看到内容」一条后新增一条：

  > **一次交审只放一个模块。** 一个模块的 Spec、Plan 审完、构建、验收后，才开始下一个模块的 Spec；几个模块要合发一个版本也一样，
  > 「一起发版」不等于「一起审」。几个模块一起审只有两种情形：用户明确要求的「按需求批量前置审」，以及开关为 `on` 时协调会话汇总交审。
  > 这两种情形都按模块分组呈现：每个模块一节，节内依次是 Spec 要点、Plan 要点、任务，模块之间按 Build order 排；不按产物类型横着排成
  > 「Spec 一、Spec 二……Plan 一、Plan 二……」。agent 不主动提议合并交审。能力图评审一次看全所有模块的拆分，不算合并交审。

- 「按需求批量前置审」第一段改为：只在用户明确要求时使用（一个需求拆成的多个模块，用户说要一次审完），agent 不主动提议；呈现按上面的分组
  写法。其余段落不变。
- 「返工与小模块」中「确需各自成模块时，用『按需求批量前置审』一次交审」改为「确需各自成模块、用户也要求一次审完时，用『按需求批量前置审』」，
  其后内容不变。
- 「协调会话的批准与合并」一节补一句：汇总几个模块的交审时按上面的分组写法呈现。

## Testing strategy

- 先写断言并确认变红（`test_workflow_checkpoints.py`）：新一条含「一次交审只放一个模块」「一起发版」「按模块分组」「Build order」「不按产物类型」
  「不主动提议」「能力图评审」；「按需求批量前置审」含「只在用户明确要求时」；「返工与小模块」不再出现 agent 自行决定的写法；「协调会话的批准与合并」
  含分组一句；两份模板与约定块文档含新增行。现有断言（如「按需求批量前置审」里的 `activeModule`、`80%`）保持不变。
- 从 0.70.1 的约定块用 `setup-convention --replace` 升级，两边宿主退出码 0，不需要 `--accept-removals`。
- 发版后两边宿主各跑一次真实会话：给一个有两个未开工模块的临时项目，让 agent 「把这两个模块做了」，不提怎么审；看它是否只交第一个模块的
  Spec，不把两份 Spec 一起交。结果如实记录。

## Boundaries

- Always：模板只新增行；规则只有一个出处；不改钩子与命令。
- Ask first：让钩子检测「一次交了几个模块」；改 `combined` 节奏；改能力图评审的交审方式。
- Never：替 module-crew 改它的汇总正文；在仓库文件、提交信息或 PR 中写入其他私有项目的名称、模块或编号。

  的写法已收紧。
