# 检查点与下一步预告

本文件是所有宿主、tracker 与串行阶段的共享交互契约。只在阶段交接、请求确认、缺信息、执行失败或用户暂停等有意义的检查点使用，不在每次内部工具调用前停下来。

检查点必须结合本轮真实证据说明五件事，可以用一段话表达：

1. 已完成的具体成果，以及已运行的验证、结果和未验证项。
2. 当前为何停下：阶段完成、缺信息、待授权、执行失败、结果未知或用户暂停。
3. 需要确认的具体范围；已有授权涵盖时明确“无需确认”，继续工作，不重复索取同一授权。
4. 后续第一步是什么，指明文件、命令、仓库、分支或远端对象；仍缺条件时明确该前提，不承诺当前无法执行的操作。
5. 下一次停止条件：什么结果可评审，或什么缺信息、失败、越界决策会阻止继续。

不要从文件存在、phase 名称或单一退出码推导执行授权。远端检查跳过时不能声称远端校验通过。按实际调用路径作预告；本地阶段不得建议立即绑定、同步、取任务或交付。

## 项目级审查 → 缺陷处理

项目级审查复用 agent-skills 的 `code-review-and-quality` 五维检查和修复技能；它与单个 diff/PR 的批准评审不同。开始一个审查批次时，先写明基准提交或快照、模块/路径范围、排除项和下一停点；有能力图时优先按现有模块划定范围，过大的项目拆成有限批次。每个预定范围做一次系统检查；候选发现只针对结论做定向核实，不因普通“继续”反复重扫已覆盖范围。证据不足时记为“待调查”，写明缺少的证据，不用无期限深挖来延迟收束。

多轮审查保留一份可恢复的审查报告或等价检查点：批次和基准、已覆盖/总范围、已确认/待调查/排除/重复的稳定发现编号、证据、影响、验证缺口、P0/P1/P2 处理优先级、待入账数与下一停点。agent-skills 的 Critical/Required/Optional 审查结论与 P 级处理优先级分别记录，不自动换算；同一根因的重复发现合并证据。没有发现也明确报告零发现和未覆盖范围。报告写入仓库前检查敏感内容，不自动提交或发布。

预定范围已覆盖、候选均已分类时，明确宣布“本批次审查完成”，列出遗留风险和下一步。**审查完成**只说明发现与分级已收束，不等于**事项已入账**、已修复或可合并。P0 或可能造成重大安全/数据损失的发现立即报告，暂停扩大扫描并标明未覆盖范围，优先进入处置；仅要求只读审查时只报告，不擅自建单或修改代码。新证据或用户明确扩展范围可另开批次，保留原基准和结论。

审查冻结后，普通“继续”只推进最近预告的查重、入账、计划或下一项修复，并显示已覆盖/总范围、待调查、待入账、待修复的数量；不能默默重新开启泛扫。可执行的缺陷先按根因查重：选用且已启用 Local 账本时走 `ticket` skill 的 `found`／`absent`／`unknown` 与读回规则。Local 未启用、归属不明或读取失败时标为待入账。GitHub 仓库仍可选 Local；Git remote、旧 tracker state、Proposal Issue 和本地 `DONE` 均不能推断日常事项目标。

明确选用 GitHub/GitLab 普通 Issue 时，按本批目标使用 `hosted-ticket-workflow` skill：完整分页查重后复核同根因候选，`rootCauseReviewRequired` 未解决前不发布；对精确目标、可见性和脱敏内容逐项授权，写入后读回 ID/URL 才算“事项已入账”。查询不完整、目标未知、标记冲突或写入结果未知均保留“待入账”，不自动重发。后续批次改选目标不迁移旧事项，不恢复旧 bridge。已确认 bug 的简单修复可接 agent-skills 的 `debugging-and-error-recovery`、TDD 和代码复审；多步骤修复按现有模块的 plan/todo 切片，不覆盖进行中的任务；独立新能力才走 add-module 或 Proposal。Local 事项经 GitHub PR 交付时继续按下方 PR 检查点对账。

## 阶段交接

- **设计 → 计划**：列明已确认/待确认的设计决策和计划路径；确认范围内先生成正式计划。若实施已有授权，计划完成时预告首个切片后继续；否则展示计划及具体实施范围后停。
- **计划 → 实现**：指出首个失败测试、实现文件和验证命令；已授权则无需确认，按切片推进。超出设计的决策、无法恢复的失败或约定验收节点是停点。
- **实现 → 验证**：说明代码完成到哪里、将运行哪些检查和环境。已授权验证直接运行；下一停点是失败诊断或完整验证结果，不能提前声称通过。
- **验证失败**：给出失败命令、退出码、证据和影响；下一步先最小复现/定位，再在已授权范围修复并复验。缺少决策时明确所需信息，不降低标准或删除反向用例来换绿灯。
- **交付前**：展示目标仓库、分支、Issue/PR/MR、具体写入内容和验证结果。对未授权远端步骤取得针对性确认；已获授权则不重复询问，Plan 的 `gate` 检查点写明的授权视为已获授权。首步按实际路径是只读核对、推送还是创建 PR，必须准确写明；结果核实或未知时停止扩展操作。
- **验收后接着写下一份 Spec**：最终 gate 获批后，下一个模块已在能力图里、用户也没说要停时，直接开始写它的 Spec，不为“是否开始”
  另停一次；写完照常交审。验收消息里预告这一步，并提示要先释放上下文的话先发 `/compact`。下一个模块还要新插入能力图时不适用，
  照旧先给用户看能力图新行。
- **PR 创建后**：若本次工作已绑定 Local 事项，读回 PR 地址和状态，把 PR 地址及本 PR 覆盖范围逐条写回关联事项；私有事项的标题与编号不因关联而写入公开 PR。写入失败时报告关联未完成，不把 PR 当成事项关闭证据。PR 未合并时保持事项开放。
- **PR 合并后**：一旦获知合并，核对精确 PR 的 merged 状态、合并提交和 CI／验收结果，并逐条写回关联的 Local 事项。只有某事项的全部范围都已交付、验证通过且已有关闭授权时才关闭，并读回关闭状态；多个 PR 中只合并了一部分、仍待部署／验收、结果未知或写回失败时保持开放，说明剩余条件。不能仅凭 PR 合并或本地 `DONE` 推断事项已关闭。没有可用的本机执行会话时，下次交付检查点须补做这项对账，不声称 GitHub 事件已自动修改本地账本。
- **Proposal 晋级 PR 合并后**：运行 `proposal-promotion-proof --prove`；`proved` 且 `closeoutPending` 为 `true` 时，接着预览 `proposal-closeout`，把收尾记录全文给用户并取得针对这一条 Proposal 的授权后才写入，并读回 `verified`。只把标签改成 `promoted` 不会关闭事项，不能当作收尾；proof 不成立或读不到时照实报告，事项保持开放。
- **托管 Issue 的 PR/MR 合并后**：按 `hosted-ticket-workflow` 对每个 Issue 读回合并提交，核对本项的覆盖范围和真实 CI／验收证据；先记录并读回处理结论，再按关闭授权逐项关闭并读回。平台自动关闭只是一条当前状态事实，不能替代验证。未合并、仅部分覆盖或证据未知时保持未完成结论。

## Plan 检查点分级

Plan 里的每个检查点标为 `gate` 或 `report`，写在检查点标题里（例如 `Checkpoint 1（report）`）：

- **`gate`**：停下，按本文开头的五件事展示结果，等用户明确确认后再继续。
- **`report`**：把已运行的验证命令、结果和未验证项记入 todo 的该项，然后直接继续；不停、不倒计时、不等回复。
- **未标注的检查点按 `gate` 处理。**
- **Plan 获批后连续执行到下一个 `gate`。** 途中的 task 与 `report` 检查点都不结束回合，也不为“是否继续”向用户发问；
  BUILDING 阶段的阶段提示会写出下一个 `gate`（`Next gate`）。
- **最终验收列出实际改动的文件。** 模块 Plan 的最后一个 `gate` 检查点，除开头的五件事外，还要在对话里列出本模块相对
  开始前实际改动的文件：分新增、修改、删除并带行数，取自版本库的差异统计，不凭记忆；文件多时按目录归并、只展开关键文件；
  单独标出超出 Plan 预计影响面的文件并说明原因，没有就写“无”。项目没有按任务提交时，列相对上次提交的全部未提交改动并
  照实说明；项目不在版本库里时，说明清单不是取自版本库。只给链接或只说“见差异”不算。途中的其他检查点不要求。
  项目打开了多模块并行开关、本模块 Spec 写了并行边界时，清单里还要标出超出并行边界的文件，见「并行边界」一节。
- **最终验收的提交包含勾选与状态记录。** 最终 gate 的批准包含提交时，先勾上这个 gate、更新 `.agent/state.json` 以及项目
  惯例里要更新的其他状态记录，把它们列进待批准的提交清单，一并提交，这样提交本身就记录了模块完成。批准不含提交时，照实说明
  这些改动留在工作区、尚未提交。
- **最终验收可以一并复审修订过的 Spec。** 构建中补改了已批准的 Spec（阶段提示报告“批准后已修订”）时，最终 gate 的验收消息
  除上面的内容外，原样附上 Spec 的改动差异（新增与删除的行，或改前改后对照），并写明“批准本次验收即同时批准修订后的 Spec”。
  用户批准后，先用 `review-mark` 记下 Spec 的批准，再勾选与提交。没附差异、只给一句概述时，验收的批准不算 Spec 复审，Spec 仍按
  「评审状态标记」单独复审。构建途中的修改若会改变后续任务的做法，照旧当场停下复审，不留到验收。
- **任务做完的结果带上文件数与提交号。** 向用户报告一个任务做完时，带上它改动了几个文件和对应的提交号；没有提交时只说
  文件数。不展开清单。
- **异常停点不受分级影响**，任何级别下都停：测试改不红、Spec 没覆盖的决策（这个决策会影响以后的设计时，停下的同时问是否记一份 ADR）、高风险不可逆改动、权限被拒、结果未知、同一个 gate 因外部原因再次挡住。
- **同一个 gate 因外部原因再次挡住时交用户决定。** 外部原因指 agent 自己改不了的：上游依赖还没修复、缺权限或凭据、
  需要用户在质量与进度之间取舍。第二次因同一外部原因过不去时就停下，把可选的做法和各自代价摆出来——挂起模块（可用
  `module-suspend --reason` 记下原因）、接受风险并写明、换方案——由用户决定；不按默认推荐继续重试，也不自己选一个接着做。

远端写入（推送、开 PR/MR、建 tag 或 Release）只有当 Plan 的 `gate` 检查点逐项写明授权时才免问，例如“本 Plan 获批即授权
推送并开模块 PR”；没写的步骤照旧在交付前询问。合并永远由用户进行，任何 Plan 都不能授权 agent 合并。本地集成分支有唯一例外：项目打开了多模块并行开关时，见「协调会话的批准与合并」一节。

## 评审节奏

单个模块的 Spec 与 Plan 怎么审，由项目配置 `.agent/config.json` 的 `reviewCadence` 决定（`/spec-guard:config` 查看）：

- **`separate`（默认，未设置时也按它）**：写入能力图后先给 Spec，批准后再写 Plan，Plan 再单独批准。
- **`combined`**：写入能力图后一次写好 Spec、Plan 与 todo 一起给用户，用户一次批准即同时批准两者，并按 Plan 的 `gate`
  检查点写明的授权推进。出现以下任一情况时退回 `separate`，先单独审 Spec：Spec 里有能力图预览时没确认过的新决策、
  范围不清、高风险或不可逆的改动。退回时说明是哪一种。

`separate` 节奏下，agent 在一个会话里第一次交审时说明一次：这个项目也可以改为 `combined`（Spec 与 Plan 一起审、一次批准），
用 `/spec-guard:config`（Codex：`spec-guard-ops` 的 config 一节）设置；之后不再重复。小步快走、两次批准之间只隔几分钟的
工作更适合 `combined`；决策多或风险高的工作留在 `separate`。

两种节奏下人工闸门都在，合并永远由用户进行。本地集成分支有唯一例外：项目打开了多模块并行开关时，见「协调会话的批准与合并」一节。多个模块一次审完走下一节「按需求批量前置审」，与本节互不替代。

## 评审状态标记

`spec/<id>.md` 与 `tasks/<id>/plan.md` 各可带一行评审状态标记（独占一行，每个文件至多一行；围栏代码块里的是示例，不算）：

```text
<!-- spec-guard: review pending -->
<!-- spec-guard: review approved <digest> -->     ← Spec，digest 是批准时的内容指纹
<!-- spec-guard: review approved -->              ← Plan
```

- **写出 Spec 或 Plan 交用户审核时标 `pending`**（写文件时直接带上这一行，或用 `review-mark`）。当前模块待审核时，
  阶段提示报告“等待用户审核”，不建议写 Plan 或继续构建；`combined` 节奏下 Spec 待审核时照常写出 Plan，两份一起交审。
- **`approved` 只在用户于当前对话明确批准这份 Spec 或 Plan 之后，用 `/spec-guard:review-mark`（Codex：`spec-guard-ops`
  的 review-mark 一节）写入**：先预览，给用户看过再 `--confirm`。含糊的“继续”“看起来可以”不算批准，先问清楚。
  不得为了消除阶段提示而自行写入。由哪个会话写：项目打开了多模块并行开关时，见「协调会话的批准与合并」一节。
- **获批后先记录，再动手。** 写入 `approved` 是用户批准后的第一个动作，先于任何代码改动、写 Plan 或勾选 todo；
  标记还是 `pending` 时已经在改代码，后续会话读到的就是一份过期的状态。
- **标记不是授权来源。** 它只是让后续会话读得到的记录；用户的批准原话以对话为准，检查点上该取得的确认照旧取得。
- **Spec 修订后须复审。** 批准标记绑定 Spec 的内容指纹，批准后内容有变，阶段提示与 `verify-artifacts` 会报告
  “批准后已修订”：把修订内容交用户过目，批准后重新运行 `review-mark` 记录。口头同意过的修改建议不等于看过改后的 Spec。
- **交审要让用户看到内容。** 交审是把内容放到用户面前，不是通知用户文件写好了。在对话正文里给出：
  - Spec：目标；范围内与范围外；关键决策与取舍；假设；验收标准；未决问题；文档建议（见「文档建议」一节）。
  - Plan：每个任务与它的验证方式；检查点及其类型（`gate` 停下、`report` 继续）；影响面（会改哪些地方）；风险。

  短文件可以贴全文；长文件给上述要点并附文件位置。只给链接、只给一句概述、只列任务标题都不算交审。
  要点写在本轮的对话正文里，放在任何会结束本轮的确认框（例如宿主的“下一步”框）之前：确认框一出现这一轮就结束，只出现在
  确认框摘要里的内容不算交审。
  写明这次批准授权什么：批准 Spec 之后做什么；批准 Plan 之后连续执行到哪个 `gate`、是否含推送与开 PR。
  `combined` 节奏下一次交审同时呈现两份的要点，并说明一次批准同时批准 Spec 与 Plan。
  用户没有在对话里看到内容时给出的批准不记为 `approved`：先补上内容，再请用户确认。
- **请求审核时说明怎么批准。** 呈现内容之后加一句：回复“批准”即可，“继续”不会被记为批准。这一句不能替代内容。
  不要等用户说了“继续”再解释；示范用最短的可接受说法，不要求用户复述一整句。
- **没有标记的文件判定照旧**，阶段提示只在建议写 Plan 时加一句“Spec 获批后”，Plan 没有标记时 `Next gate` 一行用中性说明、
  不说连续执行。既有项目不必补标记。
- **评审状态只看标记。** Spec 与 Plan 的正文不写“待审核”“已批准”“尚未批准”这类状态：正文里的状态批准之后就过时，
  以后读文件的人会照正文理解。状态只由那一行标记表达。
- **既有项目补标记要单独确认。** 要给此前确认过的 Spec 或 Plan 补 `approved`，先预览并向用户单独确认一次，
  不得依据此前含糊的答复补记。Spec 没有标记不妨碍单独记录 Plan 的批准；Spec 标着待审核或已修订时，先把 Spec 交用户审核。

## 外部审查意见

装了 delegate 时，阶段提示会在 Spec 待审、Plan 待审、最终验收这三个检查点多一行：这一项值得另一个 agent 只读复核时
（跨模块、有取舍、不可逆、信息不足、有接口提案、Task 多），可以提议用 delegate 审查，能否运行以 delegate 自己的体检为准。

- **只提议，不发起。** 用户同意后才发起；审查结论只作参考，不算用户批准，也不据此写评审标记。
- **记在哪里。** 小节标题写 `## 外部审查意见`（英文产物写 `## External review`）。Spec 交审时写在 `spec/<id>.md`
  （这时还没批准，内容随 Spec 一起审）；之后写在 `tasks/<id>/todo.md`（todo 不参与评审指纹，写入不会让已批准的 Spec、
  Plan 变成“批准后已修订”）。
- **写什么。** 按 delegate 审查报告的固定格式（JSON `schema_version` 1）引用：来源（delegate）、后端、`execution_status`、
  `review_outcome`、findings 条数、审查范围指纹（`scope` 的 `baseline` 与 `diff_sha256`），有未审到的部分（unreviewed）时注明。
  报告里没有严重程度，不写也不推断。
- **怎么读结论。** 只有 `execution_status` 为 `completed`，且 `review_outcome` 为 `findings` 或 `no_findings_in_scope`，才算有结论；
  `no_findings_in_scope` 只说明审查范围内没找到问题，不等于没有缺陷。`inconclusive` 或没有完成（`conditions_missing`、`failed`、
  `timed_out`、`cancelled`）时，记一行「未得出结论」，写明状态和原因，这不算拒绝。报告里的 `limitations` 有内容时一并注明。
- **用户不需要时**，在当时该写的那个文件里加一行 `<!-- spec-guard: external-review declined -->`。
- **接口不兼容时不提示。** 提示前会读 delegate 安装目录里的 `interface.json`：主版本在 1.x 时，命令名取自文件；文件不存在或读不懂时，
  照常提示；主版本不在 1.x 时，不出这一行（命令和报告格式可能都已经变了）。
- **每个模块只提示一次。** Spec 或 todo 里，这个小节有内容或有拒绝标记，后续检查点都不再出现这一行。

## 文档建议

没人问，就没人提文档；跨模块的文档单看一个模块也想不到。所以在三个位置各问一次，每个位置问的层次不同：

- **能力图评审**（写完或大改能力图、交用户确认模块拆分时）：跨模块、开工前就该有的文档，例如总览、术语表、架构边界、
  关键技术选型的 ADR。它们决定各个模块按什么约定写，做完再补时前面的模块已经各写各的。项目打开了多模块并行开关时，
  同一停点还要给出并行评估，见「并行评估」一节。
- **Spec 交审**（每个模块）：本模块自己的文档，例如接口契约、状态机、模块内的取舍。
- **能力图全部完成**（最后一个模块最终验收的那次停顿）：收尾文档，按实际做出来的东西更新总览、使用说明、交接文档，
  并核对能力图评审时定下的文档是否已与实际脱节。

提建议之前先想范围，不套清单：

1. 这个项目是什么、给谁用：看能力图的目标、README 与已有文档。
2. 这类项目的使用者和维护者分别要看什么：参考文档基线的类别（产品方向、架构、开发入口、使用说明、接口契约），
   项目建了文档基线就以基线为准。
3. 已有的文档里，哪些会因这次的工作过时。

README 默认在候选里：能力图评审与能力图全部完成这两处一定要对 README 表态（新建、更新或不用改）；单个模块的 Spec 交审
只在这个模块改变了使用方式时才提它。

每条建议说清写什么、为什么现在写、解决什么问题；没有就写“无”，多数模块应当是“无”。能力图评审与 Spec 交审时用户采纳的，
写进相应模块的 Plan 成为普通任务；能力图全部完成时采纳的，另开一个收尾模块按正常流程写，不在已完成的模块里补。用户拒绝的
不再就同一层次重复提。建议不卡验收，是否先查资料由 agent 判断；不自动生成文档或 ADR，已完成的模块不补建议。

## 并行评估（moduleConcurrency 为 on 时）

先用 `/spec-guard:config`（Codex：`spec-guard-ops` 的 config）看 `moduleConcurrency`：不是 `on`（包括未设置、`off` 和配置无效）时
本节不适用，交审内容与以前相同。

是不是值得几个模块同时开发，取决于能力图怎么拆，拆模块的时候最容易看清。所以只在两个时机评估：能力图评审（写完或大改能力图、
交用户确认模块拆分时），以及中途接手的项目、用户明确要求评估时。用 `add-module` 插入单个模块不算能力图评审；也不在阶段交接或
每轮回复里反复提醒。评估结论写在能力图评审的交审正文里，与文档建议并列。

**两条硬门槛**，任一条不满足就写「不建议并行」，并说明缺什么：

- 至少有一波能同时开工 2 个及以上模块：它们彼此没有依赖，或依赖的模块已经完成，或依赖的接口已经写进提供方模块的 Spec；
- 有干净的集成基线：用来合并各模块的本地分支没有未提交的改动，项目 Spec 的 Commands 一节里的完整检查能在本地跑通。
  没有实际跑过就写「未核实」，不当作已满足。

**三项参考**，不决定结论，只影响怎么建议：

- 文件分区：同一波的模块是不是各改各的目录；
- 共享接口：有没有好几个模块要用、但还没定下来的接口；
- 热点文件：锁文件、根配置、迁移、测试资源这类人人都要改的文件有多少。

**结论写成对 Build order 的建议：** 哪几个模块可以写成逗号组（逗号分隔的模块表示可以同时进行），哪些模块值得往前挪，各自为什么。
关键路径（最长的依赖链）和每个模块挡住的下游模块数只在这里算，不写进能力图，也不进 `/map`。

拆分的判据是「能否独立开发」：同时进行的模块不改同一批文件，依赖要么已经合入，要么接口已经定好。粒度是结果不是目标，能粗就粗，
不为了并行把模块拆碎。模块之间的衔接沿用现有做法：写成上一模块追加的任务，或下一模块的第一个任务；只有牵涉好几个并行模块、
或要改不归任何模块的文件时，才建议单设一个联调模块。「公共预置」也是普通模块，排在第一次有 2 个以上模块同时开工之前。

这些都只是建议。用户采纳后改 Build order 仍然是修改能力图：按「需求来源与回告」追加变更记录，交用户复审。

## 并行边界（moduleConcurrency 为 on 时）

与「并行评估」一样，先看 `moduleConcurrency`：不是 `on` 时本节不适用，Spec 的写法、verify-artifacts 和最终验收都与以前相同。

几个模块同时开发的前提是不改同一批文件。所以开关为 `on` 时，每个还没完成的模块在 Spec 里写一节并行边界，声明它独占哪些路径：

```markdown
## 并行边界

- 独占：`apps/billing/`、`packages/billing-api/`、`docs/billing.md`
- 公共：锁文件、迁移
```

- 标题写 `## 并行边界`；英文产物写 `## Concurrency boundary`，两行分别是 `- Exclusive:` 与 `- Shared:`。
- **独占**：每个路径放在反引号里，用 `、` 或 `,` 分隔。以 `/` 结尾的是目录，覆盖其下所有子孙；不以 `/` 结尾的是单个文件。
  路径相对项目根目录，不以 `/` 开头，不含 `..`，不用通配符。本模块自己的 `spec/<id>.md` 与 `tasks/<id>/` 总算在边界内，不用写。
- **公共**（可省略）：本模块预计要改的公共文件类别，只从四类里选：全局配置、锁文件、迁移、测试资源（英文 `global-config`、
  `lockfile`、`migration`、`test-resource`）；不需要写「无」。公共文件不归任何模块，模块要改时向协调的一方提出；这一行只是预告。

写在哪、谁来查：

- **Spec 交审**时，要点里加上并行边界：独占哪些路径、预计动哪类公共文件。
- **verify-artifacts** 只检查未完成模块的 Spec：格式正确通过，缺这一节只警告（无法判断与其他模块是否冲突），格式错误判失败。
  已完成的模块不检查，所以中途打开开关的项目不会一下子全部变红。
- **最终验收**列改动文件时，用越界检查对照集成基线（本模块开工时所在的那个提交或分支）：

  ```bash
  python3 -B "$ROOT/hooks/module_scope.py" check --project "$PROJECT" --module <id> --base <集成基线>
  ```

  把结果里 `outside` 的文件在清单中单独标为「超出并行边界」，逐个说明原因，没有就写「无」；与「超出 Plan 预计影响面」并列，
  不互相替代。越界只报告，不卡验收；是否接受由用户决定。`--base` 必须给，检查不会自己猜集成基线。

## 协调会话的批准与合并（moduleConcurrency 为 on 时）

先看 `moduleConcurrency`：不是 `on` 时本节不适用，评审标记与合并都按前面的原规则。

几个模块同时开发时，用户只在协调会话里审批，模块的 Spec、Plan 和代码由各自的模块会话写在各自的 worktree 里。本节说明这种分工下谁写评审标记、
谁做本地合并。它是「合并永远由用户进行」（见「Plan 检查点分级」与「评审节奏」）的**唯一例外**，只在三个条件同时成立时适用：开关为 `on`；由当前的
协调会话执行；合并的是用户刚批准最终验收的那一个模块。其他任何合并都不适用。

**协调会话。** 指由运行时（例如 module-crew）指定、负责收交付和集成的那个会话。同一时刻只有一个会话有写标记与本地合并的权限。

**评审标记由协调会话写，先核对内容。**

- 用户在协调会话里明确批准某个模块的 Spec 或 Plan 后，由协调会话在集成基线（它所在的 checkout）上用 `review-mark` 写 `approved`。
- 写之前，待审的文件必须已经在集成基线上，而且就是交审时给用户看的那一版：交审时记下文件所在的提交，写标记前核对文件在那之后没有变、与交审版本一致，再按原来的
  流程预览、确认。对不上就不写，重新交审。
- 模块会话收到协调会话转达的「用户已批准」，不能因此自己写 `approved`；等协调会话写好、提交后，同步集成基线拿到标记，并核对同步来的文件就是
  自己交审的那一版。转达不算用户批准，这一点与原规则相同。
- 批准仍然要明确、针对这一份文件。协调会话转达用户的决定时，带上编号和用户原话。

**本地集成分支的合并。**

- 批准绑定具体提交：最终验收的消息写明模块 id、模块分支当前的提交、集成分支当前的提交、要合入的改动和完整检查的结果，用户批准的就是这一组。
  合并前核对两边的提交都没变；任一边变了（模块又加了提交，或集成分支先合了别的模块），原批准不再适用，重新同步、重新检查、重新交用户确认。
- 一次只合一个模块。多个模块都在等时按 Build order 逐个处理，每合一个都重新核对下一个。
- 只用普通合并，不改写历史：不变基、不压缩、不强推。合并后跑项目 Spec 里 Commands 一节的完整检查。
- 检查失败时：用一个新提交撤回这一次合并，不 reset，不碰集成分支上其他模块的提交；撤回后停止后续合并，再跑一次完整检查，确认回到合并前的状态；
  把模块退回给模块会话，这个模块不算完成。撤回本身冲突、被拒绝或结果不明时，停下报告，不自动重试，也不继续合下一个。
- 合并有冲突时不由协调会话解决，退回给模块会话。
- 具体命令和顺序由运行时决定；本节只规定授权的边界和这些底线。
- **推送和远端合并（PR／MR）仍然只由用户做**，或者按「Plan 检查点分级」在 `gate` 检查点逐项写明授权后才推送。任何批准都推不出可以合并 PR。

**协调会话被替换时。** 换会话要经用户同意。换了以后旧会话立即停止写标记和合并。已经写进集成基线的标记照常有效；用户批准了但还没写成标记的，
新会话不能凭旧会话的转达或记录补写，要把内容重新给用户看、重新取得批准。还没执行的合并同理，要重新交验收、重新取得批准后才能合。

## 按需求批量前置审

一个需求拆成多个模块时，用户可以一次审完这些模块的 Spec 与 Plan。每个获批模块的 plan.md 在其 `gate` 检查点写明
“本 Plan 已于 <日期> 随同一需求批量批准”，用户的批准原话仍以对话为准，这句话只是让后续会话能读到。

模块完成后，若 Build order 中下一个未完成模块的 plan.md 带有这句，就把 `.agent/state.json` 的 `activeModule` 切到它并继续
构建，不在模块边界停下；没有这句就停在该模块的 Spec 或 Plan 评审。

连续构建时遇到模块边界的上下文提示（上下文达到窗口 70%）不停下，在当前会话继续；模块进行中达到窗口 80% 的提示出现时，
做完或记下当前 task 后停下，用一句话说明上下文已到 80%：接着做相关的工作就 `/compact`（带上重点），换到不相关的工作就
`/clear`，不贴交接文本。给出 `/compact` 或 `/clear` 时放进不带 shell 语言标签的代码块（不标或标 `text`），并说明它是发到消息输入框的
斜杠命令、不是终端命令：有的宿主会给带 `bash` 等标签的代码块加“运行”按钮，把它送进终端。agent 不自行开新会话，也不建议用户开新会话。用户在场时，边界提示照常由用户决定压缩还是清空。

## 返工与小模块

返工或修订已完成的模块：在该模块的 `tasks/<id>/todo.md` 追加未勾选的任务，在 `plan.md` 补一节说明改什么、为什么。模块因此
回到进行中，阶段提示如实显示；它在 Build order 里靠前时会重新成为当前模块，后面进行中的模块显示为暂停，做完再回去。
不在 `tasks/<id>/` 下另建带清单的文件：阶段判定只数 `todo.md`，旁路清单里没做完的项没人看得见（`verify-artifacts` 会对这种
文件给出警告）。

- `plan.md` 补了一节后，把 Plan 的评审标记改回 `pending` 并按「评审状态标记」交用户审核，批准后再继续。
- 给模块加新能力不是返工：另开模块（`add-module`），或走 Proposal。
- 两个模块之间必须做的事，写成上一个模块追加的任务，或下一个模块的第一个任务。
- 小模块：模块只盘点或接收既有实现、不新增行为时，优先并成相邻模块的一个任务。确需各自成模块时，用「按需求批量前置审」
  一次交审，Plan 里只留最后一个 `gate`，其余检查点标 `report`。在已有实现上补建能力图时尤其如此——逐个模块走全套闸门，
  用户得到的只是反复点头。

## 需求来源与回告

开发中途，需求常被会话外的人改动：别的会话发来消息、用户粘贴一段提示词、依赖方交付后发来通知。评审标记只管“改了要复审”，
不记为什么改、是谁提的；做完之后，提出的人也不会自己知道。下面三段把这件事接成闭环：记录来源、回告来源、接收回告。

**变更记录**

- 何时记：已批准的 Spec 或 Plan 被修改；评审过的能力图中已有的模块行、依赖或 Build order 被修改。
- 记在哪：被改文件的最后一节「变更记录」（英文产物写 `Change log`），没有就新建；每次修改追加一行，旧行不改：

  ```text
  - <日期>：<改了什么>。原因：<为什么改>。来源：<谁提出、经什么渠道>
  ```

- 来源只记事实：用户本人；某个会话（名称加会话 ID，名称可能被复用）；事项号；某个版本发布。不贴原文，不写其他私有项目的内容。
- 先写记录，再复审。复审交接时把新增的记录行与改动一起呈现：Spec 改动由评审标记报告“批准后已修订”，按「评审状态标记」
  复审；Plan 改动后把标记改回 `pending` 再交审。记录行不写批准状态——批准由评审标记表达，复审后再补会让 Spec 又成为已修订。
- 其他会话、粘贴的提示词、依赖方的通知提出的修改，不等于用户批准：记录后交用户复审，批准后才按新内容继续。
- 不记：评审前的修改；用 `add-module` 插入新模块；已完成模块的返工（按「返工与小模块」写在 `plan.md` 补的一节里）。
- 整个模块由别人提出时，在 Spec 的登记一句里写明提出者与渠道，供回告使用。

**回告**

- 回告谁：本模块变更记录与 Spec 登记里来源是他人（会话、事项、外部的人）的各条；来源是用户本人的不回告。
- 何时回告：对方用得上的时候——插件或可安装的包发版之后，其他项目合入主线之后。不在本地写完时回告。
- 最终 gate 交审时列「拟回告」：对象、渠道、内容（做完了什么、版本号或提交号、怎么用、与原约定的不同）。没有就写“无”。
  批准最终 gate 即批准回告，到了用得上的时刻按批准的内容发。
- 渠道：当前会话有可用的会话间通信手段（宿主的会话消息、本机通信插件等）就发，按会话 ID 找人；没有就在对话里提醒用户
  转告，给出可以直接转发的文字。不为回告安装或配置通信插件。
- 回告结果写在模块 `todo.md` 的最后一项：已告知谁、经什么渠道、哪天；或已请用户转告；或发送失败及原因。不写进 Spec。
- 这是弱提醒：回告失败、对方不在或找不到对方，都不阻塞模块完成，照实记下即可。

**接收回告**

- 收到依赖方“已完成”的回告时，先对照本项目的约定核对：接口、字段、版本、用法。
- 与约定一致：照常继续，不改文件。
- 与约定不一致：按上面「变更记录」修改相关的能力图、Spec 或 Plan，来源写这次回告，交用户复审。

## UI 自验

改了界面不等于改对了：测试证明不了按钮在不在、样式有没有错位、页面有没有白屏。任务改到用户看得到的界面（网页、原生界面、
宿主如何呈现 hook 输出）时，不论 Plan 是否预计到，都要验证：

- **按实际改动触发。** 任务做完时，agent 根据自己改了什么判断有没有改到用户看得到的界面；不靠文件后缀之类的规则判断。
  没改界面的任务不受影响。
- **在任务里验证，不等检查点。** 改了界面的那个任务，验证步骤就包括打开页面看；检查点只汇总各任务的结果，不因此多停。
- **怎么验。** 启动项目的开发服务或打开构建产物，找到改动所在的页面；对照 Spec 或任务写的预期逐项看改动处；看控制台有没有
  报错。网页用浏览器工具（内置浏览器或用户已登录的 Chrome），原生界面经用户授权用电脑操作截图核对。截几张图、看哪些尺寸
  由 agent 按改动判断。
- **怎么报。** 写清打开了哪个页面、对照了哪条预期、看到了什么；只写“已验证”不算。
- **做不了时。** 工具不可用、页面打不开或要登录、无人值守无法操作时，写“UI 未验证”并说明原因，不说已完成。
- **Plan 预计到时提前准备。** Plan 开头列出验证所需的工具并确认可用；缺失时在用到它的任务之前提前提醒用户安装或授权，
  不默默跳过验证。
- AI 验证后，人做最后的兜底审查，这一步是 `gate`。
- 例外：电脑操作永远不能用于 Claude 桌面应用自身，它的显示只能由用户查看或截图提供。

## 模块交付或推进时的 Proposal

在某个模块交付、或推进到下一个模块时，若实现中发现了独立的新需求，把它写成 Proposal 草稿，合并到远端
默认分支后才成为共享事实；不要把它塞进当前模块或任务。可用的只读入口：

- `/spec-guard:proposal-review`：任何分支查看单个 Proposal 的新鲜度与 Issue 阶段；
- `/spec-guard:proposal-promotion-preflight`、`/spec-guard:proposal-promotion-proof`：Issue 阶段标签 `proposal-stage:accepted` 加新鲜评审后的基点预检与合并后证明。

这些提醒不阻断交付或推进。Codex 中对应命令见 `spec-guard-ops` 的 proposal 一节。

## 权限、未知结果与取消

- **权限被拒绝**：说明被拒绝的操作、拒绝来源和理由，区分尚未执行与可能有部分效果。可继续已授权且不依赖该权限的工作；必须补权限时展示具体操作。不得把“继续”解释成覆盖明确拒绝。
- **结果未知**：不要盲目重试写入。先按精确对象/幂等标记只读核对已发生的效果，记录已知与未知范围；确认没有重复风险后才在已有授权内继续。核对仍无结论时停下说明所需信息。
- **取消或暂停**：保留当前成果，说明未完成项和没有排队继续的操作。最近预告立即失效；如果仍能进行用户要求的只读核对，明确其范围。不要把停止对话擅自变成生命周期归档、关闭 Issue 或删除 worktree。

“继续”只承接**最近一次明确、仍有效的下一步预告**及其授权范围。对象、范围或前提已经变化时先解释变化。它不能扩大到发布、安装更新、重启宿主、删除资源等未授权动作，更不能恢复已暂停的 initiative。无需新增授权 state、controller 或执行协议。

本规则的引用/文字检查只证明规则可发现；真实宿主是否遵守须用实际交互证据验证。不要把静态检查或判决器自检表述为宿主行为验收。
