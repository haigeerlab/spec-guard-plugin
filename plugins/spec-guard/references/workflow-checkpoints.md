# 检查点与下一步预告

本文件是所有宿主、tracker 与串行阶段的共享交互契约。只在阶段交接、请求确认、缺信息、执行失败或用户暂停等有意义的检查点使用，不在每次内部工具调用前停下来。

检查点必须结合本轮真实证据说明五件事，可以用一段话表达：

1. 已完成的具体成果，以及已运行的验证、结果和未验证项。
2. 当前为何停下：阶段完成、缺信息、待授权、执行失败、结果未知或用户暂停。
3. 需要确认的具体范围；已有授权涵盖时明确“无需确认”，继续工作，不重复索取同一授权。
4. 后续第一步是什么，指明文件、命令、仓库、分支或远端对象；仍缺条件时明确该前提，不承诺当前无法执行的操作。
5. 下一次停止条件：什么结果可评审，或什么缺信息、失败、越界决策会阻止继续。

不要从文件存在、phase 名称或单一退出码推导执行授权。远端检查跳过时不能声称远端校验通过。按实际调用路径作预告；本地阶段不得建议立即绑定、同步、取任务或交付。

## 项目级审查 → 缺陷处理

项目级审查复用 agent-skills 的 `code-review-and-quality` 五维检查和修复技能；它与单个 diff/PR 的批准评审不同。开始一个审查批次时，先写明基准提交或快照、模块/路径范围、排除项和下一停点；有能力图时优先按现有模块划定范围，过大的项目拆成有限批次。每个预定范围做一次系统检查；候选发现只针对结论做定向核实，不因普通“继续”反复重扫已覆盖范围。证据不足时记为“待调查”，写明缺少的证据，不用无期限深挖来延迟收束。

多轮审查保留一份可恢复的审查报告或等价检查点：批次和基准、已覆盖/总范围、已确认/待调查/排除/重复的稳定发现编号、证据、影响、验证缺口、P0/P1/P2 处理优先级、待入账数与下一停点。agent-skills 的 Critical/Required/Optional 审查结论与 P 级处理优先级分别记录，不自动换算；同一根因的重复发现合并证据。没有发现也明确报告零发现和未覆盖范围。报告写入仓库前检查敏感内容，不自动提交或发布。

预定范围已覆盖、候选均已分类时，明确宣布“本批次审查完成”，列出遗留风险和下一步。**审查完成**只说明发现与分级已收束，不等于**事项已入账**、已修复或可合并。P0 或可能造成重大安全/数据损失的发现立即报告，暂停扩大扫描并标明未覆盖范围，优先进入处置；仅要求只读审查时只报告，不擅自建单或修改代码。新证据或用户明确扩展范围可另开批次，保留原基准和结论。

审查冻结后，普通“继续”只推进最近预告的查重、入账、计划或下一项修复，并显示已覆盖/总范围、待调查、待入账、待修复的数量；不能默默重新开启泛扫。可执行的缺陷先按根因查重：选用且已启用 Local 账本时走 `ticket` skill 的 `found`／`absent`／`unknown` 与读回规则。Local 未启用、归属不明或读取失败时标为待入账。GitHub 仓库仍可选 Local；Git remote、旧 tracker state、Proposal Issue 和本地 `DONE` 均不能推断日常事项目标。

明确选用 GitHub/GitLab 普通 Issue 时，按本批目标使用 `hosted-ticket-workflow` skill：完整分页查重后复核同根因候选，`rootCauseReviewRequired` 未解决前不发布；对精确目标、可见性和脱敏内容逐项授权，写入后读回 ID/URL 才算“事项已入账”。查询不完整、目标未知、标记冲突或写入结果未知均保留“待入账”，不自动重发。后续批次改选目标不迁移旧事项，不恢复旧 bridge。已确认 bug 的简单修复可接 agent-skills 的 `debugging-and-error-recovery`、TDD 和代码复审；多步骤修复按现有模块的 plan/todo 切片，不覆盖进行中的任务；独立新能力才走 add-module 或 Proposal。Local 事项经 GitHub PR 交付时继续按下方 PR 检查点对账。

## 阶段交接

- **设计 → 计划**：列明已确认/待确认的设计决策和计划路径；确认范围内先生成正式计划。若实施已有授权，计划完成时预告首个切片后继续；否则展示计划及具体实施范围后停。
- **计划 → 实现**：指出首个失败测试、实现文件和验证命令；已授权则无需确认，按切片推进。超出设计的决策、无法恢复的失败或约定验收节点是停点。
- **实现 → 验证**：说明代码完成到哪里、将运行哪些检查和环境。已授权验证直接运行；下一停点是失败诊断或完整验证结果，不能提前声称通过。
- **验证失败**：给出失败命令、退出码、证据和影响；下一步先最小复现/定位，再在已授权范围修复并复验。缺少决策时明确所需信息，不降低标准或删除反向用例来换绿灯。
- **交付前**：展示目标仓库、分支、Issue/PR/MR、具体写入内容和验证结果。对未授权远端步骤取得针对性确认；已获授权则不重复询问，Plan 的 `gate` 检查点写明的授权视为已获授权。首步按实际路径是只读核对、推送还是创建 PR，必须准确写明；结果核实或未知时停止扩展操作。
- **PR 创建后**：若本次工作已绑定 Local 事项，读回 PR 地址和状态，把 PR 地址及本 PR 覆盖范围逐条写回关联事项；私有事项的标题与编号不因关联而写入公开 PR。写入失败时报告关联未完成，不把 PR 当成事项关闭证据。PR 未合并时保持事项开放。
- **PR 合并后**：一旦获知合并，核对精确 PR 的 merged 状态、合并提交和 CI／验收结果，并逐条写回关联的 Local 事项。只有某事项的全部范围都已交付、验证通过且已有关闭授权时才关闭，并读回关闭状态；多个 PR 中只合并了一部分、仍待部署／验收、结果未知或写回失败时保持开放，说明剩余条件。不能仅凭 PR 合并或本地 `DONE` 推断事项已关闭。没有可用的本机执行会话时，下次交付检查点须补做这项对账，不声称 GitHub 事件已自动修改本地账本。
- **Proposal 晋级 PR 合并后**：运行 `proposal-promotion-proof --prove`；`proved` 且 `closeoutPending` 为 `true` 时，接着预览 `proposal-closeout`，把收尾记录全文给用户并取得针对这一条 Proposal 的授权后才写入，并读回 `verified`。只把标签改成 `promoted` 不会关闭事项，不能当作收尾；proof 不成立或读不到时照实报告，事项保持开放。
- **托管 Issue 的 PR/MR 合并后**：按 `hosted-ticket-workflow` 对每个 Issue 读回合并提交，核对本项的覆盖范围和真实 CI／验收证据；先记录并读回处理结论，再按关闭授权逐项关闭并读回。平台自动关闭只是一条当前状态事实，不能替代验证。未合并、仅部分覆盖或证据未知时保持未完成结论。

## Plan 检查点分级

Plan 里的每个检查点标为 `gate` 或 `report`，写在检查点标题里（例如 `Checkpoint 1（report）`）：

- **`gate`**：停下，按本文开头的五件事展示结果，等用户明确确认后再继续。
- **`report`**：把已运行的验证命令、结果和未验证项记入 todo 的该项，然后直接继续；不停、不倒计时、不等回复。
- **未标注的检查点按 `gate` 处理。**
- **异常停点不受分级影响**，任何级别下都停：测试改不红、Spec 没覆盖的决策、高风险不可逆改动、权限被拒、结果未知。

远端写入（推送、开 PR/MR、建 tag 或 Release）只有当 Plan 的 `gate` 检查点逐项写明授权时才免问，例如“本 Plan 获批即授权
推送并开模块 PR”；没写的步骤照旧在交付前询问。合并永远由用户进行，任何 Plan 都不能授权 agent 合并。

## 按需求批量前置审

一个需求拆成多个模块时，用户可以一次审完这些模块的 Spec 与 Plan。每个获批模块的 plan.md 在其 `gate` 检查点写明
“本 Plan 已于 <日期> 随同一需求批量批准”，用户的批准原话仍以对话为准，这句话只是让后续会话能读到。

模块完成后，若 Build order 中下一个未完成模块的 plan.md 带有这句，就把 `.agent/state.json` 的 `activeModule` 切到它并继续
构建，不在模块边界停下；没有这句就停在该模块的 Spec 或 Plan 评审。

连续构建时遇到模块边界的上下文提示（上下文达到窗口 50%）不停下，在当前会话继续；模块进行中达到窗口 80% 的提示出现时，
做完或记下当前 task 后停下，用一句话说明上下文已到 80%：接着做相关的工作就 `/compact`（带上重点），换到不相关的工作就
`/clear`，不贴交接文本。agent 不自行开新会话，也不建议用户开新会话。用户在场时，边界提示照常由用户决定压缩还是清空。

## UI 自验

模块涉及 UI 或宿主可见的显示（网页、原生界面、宿主如何呈现 hook 输出）时：

- Plan 开头列出验证所需的工具并确认可用；缺失时在用到它的检查点之前提前提醒用户安装或授权，不默默跳过验证。
- Plan 的测试检查点含一步由 AI 执行的验证：网页用浏览器工具（内置浏览器或用户已登录的 Chrome），原生界面经用户授权
  用电脑操作截图核对。
- AI 验证后，人做最后的兜底审查，这一步是 `gate`。
- 例外：电脑操作永远不能用于 Claude 桌面应用自身，它的显示只能由用户查看或截图提供。

## 模块交付或推进时的 Proposal

在某个模块交付、或推进到下一个模块时，若实现中发现了独立的新需求，把它写成 Proposal 草稿，合并到远端
默认分支后才成为共享事实；不要把它塞进当前模块或任务。可用的只读入口：

- `/spec-guard:proposal-review`：任何分支查看单个 Proposal 的新鲜度与 Issue 阶段；
- `/spec-guard:proposal-promotion-preflight`、`/spec-guard:proposal-promotion-proof`：Issue 阶段标签 `proposal-stage:accepted` 加新鲜评审后的基点预检与合并后证明。

这些提醒不阻断交付或推进。Codex 中对应命令见 `spec-guard-ops` 的 proposal 一节。

## 权限、未知结果与取消

- **权限被拒绝**：说明被拒绝的操作、拒绝来源和理由，区分尚未执行与可能有部分效果。可继续已授权且不依赖该权限的工作；必须补权限时展示具体操作。不得把“继续”解释成覆盖明确拒绝。
- **结果未知**：不要盲目重试写入。先按精确对象/幂等标记只读核对已发生的效果，记录已知与未知范围；确认没有重复风险后才在已有授权内继续。核对仍无结论时停下说明所需信息。
- **取消或暂停**：保留当前成果，说明未完成项和没有排队继续的操作。最近预告立即失效；如果仍能进行用户要求的只读核对，明确其范围。不要把停止对话擅自变成生命周期归档、关闭 Issue 或删除 worktree。

“继续”只承接**最近一次明确、仍有效的下一步预告**及其授权范围。对象、范围或前提已经变化时先解释变化。它不能扩大到发布、安装更新、重启宿主、删除资源等未授权动作，更不能恢复已暂停的 initiative。无需新增授权 state、controller 或执行协议。

本规则的引用/文字检查只证明规则可发现；真实宿主是否遵守须用实际交互证据验证。不要把静态检查或判决器自检表述为宿主行为验收。
