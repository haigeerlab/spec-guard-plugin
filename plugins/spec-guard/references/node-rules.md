# 停点规则

本文件是[共享检查点规则](workflow-checkpoints.md)在各节点的摘要，阶段提示到了节点会附上对应一节；与共享检查点规则冲突时以后者为准。

## 能力图审阅

- 需求先确认说完：先在正文给需求总结（目标、给谁用、怎样算成功、限制、不做什么、还没定的），再问「需求说完了吗？还有要补充的吗？」，只认明确确认。
- 交审要点写在本轮对话正文里、任何会结束本轮的确认框之前，只给链接或一句概述不算交审。三项：拆成哪些模块（每个模块一句话，新插入的标「新」）；
  先后顺序（谁先做、哪些可以同时做、为什么）；文档建议（跨模块、开工前就该有的文档，README 一定表态，没有写“无”）。
- 能力图审阅一次看全所有模块的拆分，不算合并交审。
- 小项之后写“注意：”与“批了会怎样：”；再列选项、各自选了会怎样，写“推荐理由：”，推荐答复放进一个可复制代码块。批准来源与在哪里答复以所装协作插件的规定为准；没装只认当前对话里的明确批准。

## Spec 交审

- 交审要点写在本轮对话正文里、任何会结束本轮的确认框之前；只给链接、只给一句概述不算交审。每一项按要求写全，不为了短而删减：
  目标；边界（总是做、先问、不做三档，范围外的事写在“不做”里）；要你确认的假设（含关键决策与取舍）；验收标准（按 AC1、AC2… 编号），逐条全列；
  未决问题（还没定、要用户回答的事，每个写清选项；没有就不写）。之后是附加项文档建议（本模块自己的文档），有才提。
- 小项之后写“注意：”（遗留建议、没验证到的、偏离计划的，没有写“无”）与“批了会怎样：”（批准后做什么）。
- 文件标批准标记 `pending`；用户明确批准后先用 review-mark 记 `approved`，再写 Plan 或动代码。“继续”不会被记为批准。
- 一次交审只放一个模块；几个模块一起审时按模块分组，每个模块一节，不按产物类型横排。
- 值得另一个 agent 复核时，装了 delegate 插件可提议只读审查，用户同意再发起；审查结论不算用户批准。
- 怎么批准：列选项、各自选了会怎样，写“推荐理由：”，推荐答复放进一个可复制代码块。批准来源与在哪里答复以所装协作插件的规定为准；没装只认当前对话里的明确批准。

## Plan 交审

- 交审要点写在本轮对话正文里、确认框之前。六项：架构决定；分几步（每个任务与它的验证方式）；会改哪些文件（影响面、新增依赖、碰不碰公共文件）；风险；
  中途会停下来问你的地方（检查点及其类型，`gate` 停下、`report` 记入 todo 后继续；列出 `gate` 并写明是否含推送与开 PR，没有中途 `gate` 写“无，做完直接交
  最终验收”）；未决问题（没有就不写）。`combined` 节奏下先写 Spec 的五项再接 Plan 的六项，说明一次批准同时批准 Spec 与 Plan。
- “批了会怎样：”写批准后连续执行到哪个 `gate`。批 Plan 按范围授权：改本仓库文件、跑测试与构建、本地提交、构建需要的装包，不按次数；
  项目自己的规则更严时，以项目为准。
- 只在这几类情况停下问用户：`gate` 检查点；远端写入；改模块范围；Spec 没覆盖的决定；不可逆或高风险操作（推送、发布、删除工作区外的文件、
  改全局配置、外发凭据、全局安装、下载脚本直接执行）；测试改不红；权限被拒；结果未知；同一模块、同一目标第二次过不去。
- 批准标记、一次一个模块、怎么批准同「Spec 交审」。

## 中途 gate

- 交审要点写在本轮对话正文里、确认框之前。三项：做到哪了（完成了哪几步、测试结果）；为什么停在这；接下来要做的那一步（具体做什么、动哪里）。
  开头的五件事落在这几项里；之后写“注意：”“批了会怎样：”。
- 同一模块、同一目标因外部原因第二次过不去，或第二次为它向用户报批时，先写“出了什么事：”，再把挂起本模块并先开可开工模块、接受风险、换方案、
  一次列全所需权限等做法和代价摆出来，由用户决定；不按默认推荐继续重试。
- 停在宿主确认前，告诉用户去哪个会话、点什么；这不算问用户做决定。

## 最终验收

- 交审要点写在本轮对话正文里、确认框之前。四项：做了什么；验收结果（按 AC 编号逐条给证据，以及完整检查的结果）；改了哪些文件；Spec 中途改过吗。
- 改了哪些文件用表格、取自版本库：写给人读的文档单独一张表放在最前，没有写“文档改动：无”；其余文件写状态、文件、行数，超出 Plan 预计影响面
  （开关 on 时还有并行边界）的单独标出；本模块的提交（提交号、一句话、对应任务，勾选与状态记录写作待提交放在最后一行）；新增依赖与锁文件改动，
  都没有写“新增依赖、锁文件改动：无”。界面任务的自验结果与截图一并摆出。
- Spec 在构建中被补改过时，原样附上 Spec 的改动差异，写明批准本次验收即同时批准修订后的 Spec；批准后先用 review-mark 记下 Spec 的批准，再勾选与提交。
- 拟回告：来源是他人的各条，列对象、渠道与可以原样发送的完整文字，没有写“无”；批准本 gate 即同意按这段文字发送，对外渠道同样；到发送时内容要变，
  把改后的全文重新给用户看。装了 agent-relay 插件时用它给对方会话发。
- “批了会怎样：”写提交什么、推送或开 PR 是否另问。批准后先勾这个 gate 与状态记录，一并提交。
- 验收获批后，下一个模块已在能力图里且用户没说停时，直接写它的 Spec 并交审；验收消息预告这一步，并提示可先 `/compact`。
