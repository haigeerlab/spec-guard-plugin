# 托管日常事项工作流：实施计划草稿

状态：设计已获用户同意；Proposal `hosted-ticket-workflow` 尚未发布、接受或晋级。此文只安排未来切片，不是 `tasks/hosted-ticket-workflow/plan.md`，不启动实现或创建远端 Issue。正式模块 Spec 与 Plan 应在 Proposal 晋级后依据评审意见落地。

## 架构与顺序

- Local 继续通过 Epiq `ticket` skill；GitHub/GitLab 走一个新的按需日常入口，仅复用可与 Epiq 解耦的安全传输基础，不调用 Local 移交发布器。
- 每批审查或直接事项只选一次目标；无项目级模式文件，不读取旧 tracker state 作为路由。
- 托管 Issue 是成功入账后的事实源。创建前的最小私有意图仅用于响应未知时按标记读回；不建立通用同步日志。
- 交付对账独立于 PR/MR 创建和合并：只有目标事项范围完成、验证通过且有关闭授权才更新并读回状态。

## 切片与验收

1. **只读目标与查重。** 从 `ticket` 入口对精确 GitHub/GitLab host/project 核验可见性、权限、开放及已关闭 Issue；排除 GitHub PR 与 GitLab 系统 note。用户可读到 `found / absent / unknown / conflict` 和下一步，分页不完整不能是 `absent`。验证：CLI 桩的完整、截断、403、混入 PR/note 场景；至少一个真实目标只读核对。
2. **单条安全创建。** 从已确认的发现或直接事项草稿得到稳定请求编号；在 `ticket` 入口预览精确目标、脱敏内容和来源标记；在具体授权后创建，读回 ID/URL，并把结果写回审查报告。响应丢失先按标记对账，不能自动重发。验证：成功、4xx、超时、重复标记、跨会话恢复及 linked worktree 并发；如需私有意图文件，只保留对账必需字段。
3. **讨论与交付收尾。** 从已读回的 Issue 进入修复流程；实质范围变化先追加决定评论。按精确 PR/MR 的合并、CI/验收及覆盖范围逐项核对，处理平台自动关闭，再按授权关闭/读回 Issue。验证：部分合并、未部署、人工改动、自动关闭、网络失败时不虚报完成。
4. **批次与双宿主一致性。** 让审查共享检查点在 Local/GitHub/GitLab 上显示同一语义与剩余数量；更新 Claude/Codex 入口和文档。验证：已冻结审查后的多轮“继续”进入逐项处理；只读审查不会建单；GitHub 仓库选 Local 不被改路由。
5. **受控真实验证与回归。** 经精确目标与内容授权后，各在 GitHub/GitLab 做至少一次真实建单、读回、讨论与关闭闭环；真实目标不可用时记录未验证，不以桩测试代替。运行 Local 账本/移交、Proposal 只读、退役 bridge、phase/产物及 `scripts/validate.sh` 回归。

切片 1 → 2 → 3 → 4 → 5。每片有独立可观察结果；若前片的安全边界无法验证，不推进后片的远端写入。

## 风险、缩减和检查点

- 远端平台没有原子“同根因唯一”创建；完整查重、稳定标记和本地串行化只能降低重复概率。两个独立 clone 同时写入时保留冲突事实，不宣称绝对防重。
- 底层代码若难以从 Local 移交模块安全抽取，就只复用稳定的小型命令/分页/响应校验函数；不得为复用而重构完整移交流程。
- 不加项目级 Tracker 配置、后台监听、双向同步、自动迁移、工作树绑定或新 phase 状态。任一新增层都须证明其直接支撑上述验收，否则从计划删除。
- Proposal 发布/接受/晋级是实现前的治理门槛；第 2、3、5 片涉及外部写入，实际执行时分别预览目标内容并取得授权。
