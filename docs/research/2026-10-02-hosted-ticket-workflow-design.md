# 托管日常事项工作流：设计与精简审查

状态：待用户评审的设计草案；尚未提交 Proposal、插入能力图或开始实现。基线：`main` 的 `334a722`（PR #123 已合并）。

## 问题与现有边界

项目审查现在会在有限批次后收束发现。选用 Local 时，`ticket` skill 可查重、建单、读回，并在 PR 合并后的可用本机会话中对账；选用 GitHub/GitLab 日常 Issue 时，当前只生成待外部交接清单。旧 tracker bridge 的 Issue 投影、取任务、工作树绑定与交付同步已退役；Proposal Issue 仅供其独立的只读流程使用。`local-ticket-portability` 能把选中的 Local 事项显式移交到远端，但不接管日常托管事项。

目标是让 Local、GitHub、GitLab 的**事项语义**一致：确认来源 → 查重 → 取得稳定身份 → 记录实现与验证 → 交付后核对 → 按实际状态关闭。三者可以有不同的命令、权限和页面；GitHub/GitLab 代码仓库也可以继续把 Local 作为事项目标。

推荐按批次或事项选择目标：代码仓库的 Git remote 与事项归属是两个独立事实，现有 Local 事项经 GitHub PR 交付已经证明不能混为一谈；固定项目模式会增加切换、旧事项归属和配置漂移三类状态；审查批次只需选一次目标并随发现保留，因而无需每轮重复询问。直接受理的 bug 同样只选择一次。

## 设计决定

1. **一个候选能力，不恢复 Bridge。** 候选模块 `hosted-ticket-workflow` 只补 GitHub/GitLab 普通 Issue 的按需日常受理、读回、讨论和关闭。Local 沿用 Epiq 入口；共享的只是 `ticket` 与审查检查点中的处理语义。模块不得做任务投影、自动认领、工作树绑定、后台双向同步或修改 Proposal 流程。正式模块 ID、依赖及锚点在 Proposal 中核对。
2. **每批明确事项目标。** 审查批次或直接受理的事项明确选择 `local|github|gitlab`；托管目标还要给出 `host` 与 `project`。一次批次内沿用这个选择，不每轮重问；已启用且归属明确的 Local 账本维持现有默认行为，但写入前也要显示本次选择。其他未指定目标的场景先询问。不凭 Git remote 或旧 `.agent/state.json` 推断远端目标，也不新建一份项目级模式配置。每条事项记住实际 ID/URL 与目标；后续改选目标只影响新事项，不隐式迁移或批量关闭。
3. **参考传输，隔离业务状态。** GitHub/GitLab 现有移交代码已有目标校验、分页、Issue/PR 区分和 API 响应验证；优先复用可独立于 Epiq 的小型底层函数，不为此大改移交模块。日常入口不调用移交发布流程，也不复用其 Local 来源映射日志；只需查询、读取、创建、追加讨论、关闭及读回，不设计所有 Tracker 的通用 CRUD 框架。实质范围变化先用可读评论留痕，再按平台事实决定是否更新正文。
4. **一次事项，一个事实来源。** 审查发现有稳定的批次/发现编号；直接受理的 bug 在远端写入前取得稳定请求编号。写入前保留最小的私有意图（目标、编号、内容摘要，不复制完整敏感正文）；审查报告或直接受理草稿承载原始需求。远端 Issue 正文放与 Proposal/Local 移交不同命名空间的来源标记。创建前查重并预览精确目标与内容，获授权后写入且按 ID/标记读回；响应丢失、列表不完整或发现多个匹配均为 `unknown/conflict`，不自动重发。意图仅用于不确定写入的恢复，读回并记录远端 URL 后可清理；实现计划须证明跨会话可读并处理 linked worktree 并发，不扩张成第二份事项账本。
5. **交付对账按事项逐条进行。** PR/MR 合并不是事项关闭事件。读回精确合并状态、提交、CI/验收和 Issue 当前状态；覆盖范围全部完成且有关闭授权时，更新并读回相应事项。平台自动关闭或人工改动以读回结果为准；部分交付、待部署、权限失败或结果未知时保持未完成结论。Local 仍按现有本机检查点对账，不假称 GitHub 事件能直接修改本机账本。

## 用户流程

1. 审查报告冻结或用户直接提交 bug。先判定是已确认缺陷、待调查、重复项或独立新能力；P0 立即报告，停止扩大审查。
2. 读本批次已选目标，或为直接事项选择一次目标；展示平台、host、project 与可见性。目标不明、不可读或无权限时停在“待入账”。
3. 按根因查询开放和已关闭事项。精确匹配则复用；查询不完整或有歧义则展示候选、等待选择；确认缺席后才展示新事项的标题、正文、影响、验收条件和目标。
4. 经本次外部发布授权后逐项创建，读回真实 Issue ID/URL 并写回审查报告或事项上下文。P1/P2 可分批预览授权；一批中某项失败不把其余项标成成功。仅要求只读审查时到第 3 步结束。
5. 复用 agent-skills 的诊断、TDD、增量实现与代码复审。复杂修复才维护相应模块 plan/todo；既有 bug 不自动变成新模块。PR/MR 交付后逐项对账，满足关闭条件才关闭并读回。

## 必须保留的边界

| 场景 | 结果 |
| --- | --- |
| GitHub 仓库选 Local；Local 账本 `foreign/unknown` | 不切换到 GitHub；先报告本地归属或读取问题。 |
| 一批发现分属不同团队或仓库 | 按事项目标拆成交接批次；同一发现不同时写入多个 Tracker。 |
| 后续批次改选目标、已有 Local/远端事项未结 | 旧事项沿原 ID/URL 处理；需迁移时另走显式移交。 |
| 查询分页耗尽、网络/认证失败、写入超时、多个标记命中 | 结果未知或冲突；保存证据并先读回/人工对账，不按“缺席”创建第二条。 |
| GitHub Issue API 混入 PR；GitLab 系统 note 或私有 note | 不能当普通事项或公开讨论证据。 |
| PR/MR 合并但只覆盖部分缺陷，或平台因关闭关键字自动关闭 Issue | 核对每项实际状态和剩余验收；不自动添加关闭关键字，也不根据合并事件批量关闭。 |
| 外部 Issue 内容含内部路径、Local 私有标题/编号或敏感证据 | 发布预览先脱敏；不自动把 Local 内容复制到公开目标。 |
| 两个独立 Agent/clone 同时创建同义事项 | 本地串行化只能缩小窗口；远端无原子唯一键时不能承诺绝对防重，重复则报告冲突并人工处理。 |

## 验收与验证

- 三种目标都能给出 `found / absent / unknown`、稳定 ID/URL、明确下一步；Local 既有行为不回归，GitHub/GitLab 不依赖 Epiq。
- GitHub/GitLab 的缺陷事项正反场景通过 CLI 桩测试；至少各一次受控真实目标读写与读回，严格区分模拟和真实证据。
- 断网、分页不完整、响应丢失、跨会话恢复、权限变化、后续批次改选目标、PR/MR 部分合并、平台自动关闭均不产生虚假“已入账/已关闭”。
- Proposal 只读套件、旧 bridge 退役扫描、Local 账本与移交回归、双宿主入口、完整 `scripts/validate.sh` 通过。

## 过度设计审查

| 候选做法 | 结论 | 理由 |
| --- | --- | --- |
| 统一 Local/GitHub/GitLab 的新运行时接口与状态机 | 删去 | Local 已有 Epiq 事实源；只共享处理语义，避免复制一套账本。 |
| 恢复旧 bridge 的任务投影、取任务和工作树绑定 | 删去 | 与缺陷入账和交付对账无关，也是明确退役的风险面。 |
| 常驻监听 GitHub/GitLab 合并事件来关闭本机 Local 事项 | 删去 | 需要服务、认证、可达性和掉线补偿；现阶段检查点对账满足按需场景。 |
| 每次远端建单都先造 Local 事项再调用完整移交 | 删去 | 无端要求 Epiq，制造双重身份与迁移成本。 |
| 自动双向同步、批量迁移或隐式目标切换 | 删去 | 会引入冲突裁决和来源不明；已有显式移交能力处理迁移。 |
| 项目级目标配置文件 | 删去 | 目标随批次/事项明确记录；再加一层模式状态会引入切换、迁移与旧 state 冲突。 |
| 不确定写入的最小私有意图 | 保留 | 响应丢失后需要稳定标记才能读回；只保存对账所需字段，不做通用事件日志。 |

审查结论：以**一个候选模块、两个托管平台的窄操作、按批次选择目标、最小写入意图**为上限。当前设计没有理由改 phase hook、Proposal、Epiq 数据模型或 setup-convention 的 local 多模块含义。剩余设计风险是远端无原子防重、私有意图跨会话恢复与独立 clone 并发；正式 Proposal 应明示这些限制，不能用“工作流相似”承诺强一致。
