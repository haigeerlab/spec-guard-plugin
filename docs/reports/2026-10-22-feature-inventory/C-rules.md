## 通用说明（适用于全表，不再逐行重复）

- **生效时机**：约定块（B/X）由 `/spec-guard:setup-convention` 写进使用者项目的 CLAUDE.md／AGENTS.md，写入后「总是」生效（对 agent 是每次会话上下文里的规则）。W 是约定块指向的细则，agent 在「阶段交接、确认、停止」时按约定块那条指针加载（S 第 6 行也要求「阶段交接、确认或停止前读取」）；也就是说 W 靠 agent 自觉加载，没有 hook 强制。
- **能否关闭**：没有逐条开关。可行途径只有三种：(a) 不运行 setup-convention；(b) 把某行移进约定块的本地段 `<!-- BEGIN:spec-guard-local -->`（`--replace` 保留本地段；删模板行需 `--accept-removals`）；(c) 少数规则挂在配置开关上（`reviewCadence`、`moduleConcurrency`、`artifactLanguage`、`dispatch`）或依赖外部条件（账本已启用、delegate／agent-relay 已安装）。下表「可关闭」一列只写**这条规则本身**有没有专属开关；写「无专属开关」即只能靠 (a)(b)。
- **能力图模块 id**：用 grep spec/CAPABILITY-MAP.md 与各 spec 正文关键词匹配得到；匹配不到的写「未找到专属模块（疑出自 xxx）」。

## 17. 最值得和使用者核对的需求疑点（按重要性）

1. **规则格式被姐妹插件牵着走（越界耦合）**：交审五类要点「名称与顺序与决策收件箱卡片相同」、「去决策收件箱答 #N」话术、「经收件枢纽转来的批准」四条件、协调会话＝module-crew 角色、派活规则里的 tier-guard 档位标记（W:158–159、195–199、318–329、341；D:9–12）。spec-guard 声明「不解析消息、不登记枢纽」，却在规则里复述了姐妹插件的契约与话术；这些应归 decision-inbox／module-crew／tier-guard 自己的规则，spec-guard 只需声明「接受什么来源的批准」。
2. **授权模型过宽且与宿主权限叠加**：批 Plan 即授权「构建需要的装包（含联网）默认放行」（W:70–73）、批准最终 gate 即批准未来回告（W:422–423）、并行开关 on 时授权 agent 本地合并（W:336–362，「合并永远由用户进行」的唯一例外）。三者都是把用户安全决定提前到一次批准里，需要和使用者确认是否真是产品想默认给的。
3. **交审/验收的格式规定过细，像某人的使用习惯**：五类要点各 4–5 小项、「注意：」「批了会怎样：」、推荐答复放不带语言标签的代码块、「批准；D1 A」写法、最终验收固定四张表（改动文件、文档、依赖、提交）、先停一轮再一起交审、验收后自动写下一份 Spec。这些使插件失去灵活性，且无逐条开关，使用者只能整块不用或移进本地段。
4. **约定块与 W 大量重复表述**：约定块 32 条里约 20 条在摘要里已写全要求，再加「细则见 W」；W 的「继续」语义、对外先给草稿、批准标记等在多处重复（3.7／4.2／4.11／5.6／13.5）；11.8 与 11.23 对「回告是否已授权」自相冲突，2.1 与 11.17 靠例外条款共存。重复造成任一处修改都要同步多处，且给 agent 带来冲突指令。
5. **越位到宿主与上游能力**：70%/80% 上下文阈值与 `/compact`／`/clear` 话术（W:376–379，hook 又注入一遍）、「不对 Claude 桌面应用用电脑操作」（W:509）、确认框之前写要点（W:178）、内置浏览器／已登录 Chrome（W:499–501）、分级审查报告 P0/P1/P2 叠加上游 Critical/Required/Optional（W:19）、三套并行文档机制（文档建议＋文档基线＋文档影响）。这些属于宿主或上游 skill 的范围，值得决定是否保留在 spec-guard 规则里。
