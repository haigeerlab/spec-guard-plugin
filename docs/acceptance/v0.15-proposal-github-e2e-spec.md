# Draft Spec: Proposal v2 mainline-review GitHub E2E acceptance

## Status

Draft only. It authorizes no external operation; the target, protected policy and
attestation process, and every GitHub or Git write require separate confirmation.

## Objective

Prove that an author branch can publish a v2 Proposal but cannot self-accept it.
Only the policy-defined mainline may evaluate the fixed remote-main candidate pool
at a module boundary. Accepted requires a human-written Issue stage and a matching
immutable attestation; promotion requires fresh preflight and strict post-merge proof.

## Fixture and actors

| Actor | Responsibility | Write authority |
| --- | --- | --- |
| Fixture maintainer | Preserve historic fixture and prepare remote-main foundation/policy. | Explicitly approved fixture objects only. |
| Proposal author | Merge a v2 Proposal to remote main. | Approved Proposal merge only. |
| Mainline chain | Discover and explicitly decide at module boundary. | None. |
| Protected acceptance process | Write attestation and separately set accepted Issue stage. | Approved evidence and label only. |
| Promotion maintainer | Create promotion branch from ready preflight and merge map, Spec, Plan only. | Approved branch and merge only. |
| Proof verifier | Run read-only proof. | None. |

## Required scenario

1. Preserve the historic main fixture at an approved legacy ref. Local state and
   historic Issues are evidence, never Proposal input.
2. Prepare remote main with foundation, no alpha/beta, and protected unique
   mainline policy.
3. Merge a v2 alpha Proposal with Integration intent, revision, immediate
   remote-main baseline and a new-module anchor after foundation.
4. Human creates one exact-marker published Issue. The author branch may read
   it but cannot get accepted-candidate or write accepted.
5. At mainline module-deliver or module-advance, discover remote-main candidates.
   Dirty sibling worktree Proposal/code must not appear.
6. Submit bounded observations and an explicit decision. Hard package,
   public-contract or anchor conflict returns needs-revision without writes;
   non-conflicting accept returns accepted-candidate only.
7. Protected human process writes matching attestation and separately sets Issue
   accepted. Fresh preflight returns ready only when policy, Issue, attestation
   and Proposal revision agree.
8. Human creates the promotion branch from baseCommit and merges only the alpha
   map row, spec/alpha.md and tasks/alpha/plan.md.
9. Proof verifies first-parent insertion, responsibility, dependencies, anchor,
   Spec, Plan and file allowlist. Only afterwards may a human mark promoted.
10. A drifted alpha is stale and cannot preflight; beta must use the resulting
    remote-main baseline.

## Boundaries and success

- No retired bridge, sync command, tracker mapping or local-state selection.
- No other-worktree uncommitted file is shared fact.
- Plugin never writes Issue, label, branch, PR, map, Spec, Plan, task or attestation.
- Branch naming is not human identity; protected policy/attestation are external
  governance prerequisites.
- Missing/mismatched evidence, duplicate identities, map drift, missing artifacts
  and extra promotion files all fail closed.

## Required approval

Confirm target, legacy ref, policy protection, mainline ref, Issue-label operation,
attestation writer, promotion branch/merge and final promoted-label operation before
execution. Until then only local/read-only work is permitted.
